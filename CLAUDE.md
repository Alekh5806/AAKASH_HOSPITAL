# Aakash Eye Hospital Project Guide

This project is a production-ready, mobile-first website for Aakash Eye Hospital. The goal is to present a clear, premium, trustworthy, and easy-to-use digital experience for a multi-branch eye hospital. Most visitors are expected to use mobile devices, so every implementation decision must protect small-screen usability first.

## Product Direction

- Build a direct, simple, patient-friendly hospital website, not a complex web app.
- Prioritize fast navigation to services, doctors, hospitals, contact numbers, WhatsApp, maps, and appointment booking.
- Keep pages focused and easy to scan. Avoid long marketing sections, unnecessary animations, and complicated interactions.
- Design for a world-class multi-branch eye hospital: professional, clinical, calm, trustworthy, and polished.
- Mobile UI/UX is the primary experience. Desktop must still look premium, but mobile should never feel like an afterthought.
- Content should be clear for patients and families, including older users who may need larger touch targets, readable text, and obvious actions.

## Tech Stack

Runtime:

- React 19
- React DOM 19
- React Router DOM 7
- Vite 8
- Framer Motion for controlled animation
- Lucide React for icons
- React Hook Form for forms
- Zod and `@hookform/resolvers` for validation

Development:

- ESLint 9 with React, hooks, and refresh plugins
- Prettier 3
- Cloudflare Pages compatible static deployment

Important commands:

```bash
npm install
npm run dev
npm run lint
npm run build
npm run preview
```

Deployment target:

- Build command: `npm run build`
- Output directory: `dist`
- Public static assets served from `public`
- No environment variables: the appointment page composes a WhatsApp message client-side and posts nothing to a server.

## Architecture Rules

- Pages live in `src/pages` and are loaded through `src/router.jsx` using lazy route modules.
- Reusable page sections live in `src/sections`.
- Shared UI primitives and layout components live in `src/components`.
- Editable content belongs in `src/data` JSON files whenever possible.
- Data access and validation helpers belong in `src/lib`.
- Global styling lives in `src/styles/global.css`; keep changes scoped and avoid unrelated rewrites.
- Namespaced stylesheets own their own components and are imported from `src/main.jsx` after `global.css`: the site header owns `src/styles/header.css` (`.hd` / `.hd__*`), the landing page owns `src/styles/landing.css` (`.lp-`), the footer owns `src/styles/footer.css` (`.ft-`), the two About pages own `src/styles/about.css` (`.ab-`), the services index owns `src/styles/services.css` (`.sv-`), the service detail page owns `src/styles/service-detail.css` (`.sd-`), the doctors page owns `src/styles/doctors.css` (`.dr` / `.dr-`), a hospital's own page owns `src/styles/branch.css` (`.br-`), the hospitals index owns `src/styles/hospitals.css` (`.hs-`), the contact page owns `src/styles/contact.css` (`.ct-`), the appointment page owns `src/styles/appointment.css` (`.ap-`), the cookie consent owns `src/styles/cookie.css` (`.ck` / `.ck__*`), and the opening curtain and the initial route wait own `src/styles/preloader.css` (`.pl` / `.pl__*` / `.pl-wait`). Never restyle these components from `global.css` or `system.css` - the header in particular used to be styled from three places at once, and one source of truth is what keeps it predictable.
- **Every `.e-link` carries an invisible `::after` halo (`inset: -10px 0`) in `system.css`**, so a 25px text link is a 45px target without the underline moving. It started as a patch on the landing page's `Meet the full team` and moved into the primitive when the service detail page turned up three more (`Visnagar`, `Ask us directly`, `See all 11`) - every `.e-link` on the site is a route, and the fix belongs where the link is defined. Measure with `elementFromPoint`; the element rect cannot see the halo.
- `.e-label` in `system.css` is `--e-ink-2`, not `--e-ink-3`: 0.72rem semibold uppercase needs 4.5:1 and `--e-ink-3` measures 2.9:1 on paper. Every section eyebrow on the site reads that one rule, so the services page no longer carries its own override. Do not lighten it back for looks.
- `src/lib/contact.js` holds the shared phone/WhatsApp/map link helpers. Use it instead of re-declaring `cleanTel`, `getPrimaryPhone`, `buildWhatsApp` or `buildMapLink` in a component. It also owns `BRANCH_STORAGE_KEY`, `storeBranch()`, `BRANCH_CHANGE_EVENT` and `getStoredBranch()` - the hospital the header stored for this reader, and the event that tells the rest of the page it changed. `Header`, the service detail page and the contact page's switchboard all read that one key, and `Header` also listens for `BRANCH_CHANGE_EVENT`, so a hospital chosen on the contact page moves the number at the top of the screen at once - a phone number offered in the page can never be a different hospital's from the one at the top of the screen. It also owns `hasBranchPage()` and `buildBranchHref()` - the one place that decides whether a hospital link opens that hospital's own page or the index with it selected - so the header, the drawer, the footer, the impact chips and the branches index can never disagree. They live here rather than in `branchData.js` so the header does not pull the doctors and services data into the root bundle for one link.
- **`src/lib/hours.js` is the one reader of a hospital's OPD hours.** Every hospital carries its own `hours` block in `branches.json` - a `schedule` of slots (a set of `days` with one `opens` and one `closes`), a `closedNote` for the days in no slot, and the `note` printed under the hours on its page - and `site.openingHours` is the network default a hospital without a block inherits, plus the one `timeZone` every hospital's clock runs on. `getBranchHours(branch)` merges the two; `getHoursRows()` derives the printed `Monday to Saturday, 9:00 AM - 6:00 PM` lines from the schedule (two slots on the same days share a row); `getOpenState()` answers the live pill; `toOpeningHoursSpecification()` feeds the JSON-LD; and the appointment flow's open days and its date check read the same block. There are no hand-written display strings any more - `site.businessHours` was the second copy that let the printed `6:00 PM` and the structured `20:00` disagree for a release, and deriving the words from the numbers is what makes that impossible. Anything that shows hours takes the hospital it is describing (`BranchStatus` takes a `branch` prop; the footer and the contact page's foot follow the reader's stored hospital and name it), because a figure for "the OPD" with no hospital attached is somebody else's on five pages out of six.
- Public media should live under `public/assets/media` and be referenced with `/assets/media/...` paths. The hero film lives in `heroes/` alongside the stills.
- Prefer existing helpers such as `SEO`, `JsonLd`, `ButtonLink`, `SmartImage`, `Reveal`, and `LazyMapFrame` before creating new primitives.
- Remove dead components, imports, CSS selectors, and unused assets when a section is removed. This site must stay clean and deployment-ready.
- **Auditing a namespaced stylesheet for dead selectors: match class names as whole tokens, never as substrings.** `jsx.includes("sv-part")` is satisfied by `sv-parts__list` and will report a genuinely dead class as live. Tokenise both sides (`/[A-Za-z0-9_-]+/g`) and compare sets.
- **A script that strips rules must not split a prelude on commas without stripping comments first.** A comment sitting above a rule is part of that rule's prelude, and comment prose contains commas: splitting `/* ... two services, so the answer ... */ .sv-match` on commas keeps the fragment before the comma, drops the half carrying the selector, and leaves an unterminated comment welded to the rule body. It fails as a CSS syntax error several hundred lines later, nowhere near the cause. Strip comments, then split.

### Hero

`src/sections/Hero.jsx` owns the `.e-hero` rules at the top of `src/styles/landing.css`.

- The hero is a muted, looping film of the hospital - the building, the atrium reception, an examination room - following the Function Health reference. It replaced a still macro photograph of an eye; `eye-macro-wide.jpg` went with it.
- The source is a 6.9s 4K60 clip that is 100MB and unusable as shipped. Everything under `public/assets/media/heroes/hero-*` is encoded from it and must be re-encoded, never hand-edited. The recipe: crop `3688:2074:0:40` first, because the scenes after the first are composited inside a 3688x2154 box and carry black padding on the right and bottom edges that `cropdetect` will not find on its own (the opening exterior shot fills the full 3840x2160, so there is no bar spanning the whole frame). Then 1920x1080 for the landscape cut and a centred `1556:2074:1066:40` crop scaled to 900x1200 for the phone. Audio is stripped - autoplay requires it and the file does not need it.
- Two encodes rather than one CSS crop. `cover` in a portrait box would throw away two thirds of the landscape frame and still push the full 1920px width over mobile data; the 3:4 cut is framed for the phone and is a third of the bytes (webm 570KB against 1.25MB). `usePhoneVariant()` picks between them with `matchMedia` at the same 760px the layout breaks at, and the `key` on the element forces the reload when it changes.
- webm (VP9) first, mp4 (H.264) second, so the smaller file wins wherever it is understood.
- The phone crop also excludes the generator watermark that sits in the lower right of the source. The landscape cut still contains it.
- The film is not load-bearing. A poster frame carries the same scene, is what `prefers-reduced-motion` opens on, and is what stays if the video never arrives; it is preloaded per breakpoint from `index.html` because it is the LCP element.
- `.e-hero__media` is `z-index: 0`, not `-1`. The pause control lives inside it so it can sit in the corner of the film at every width, and a negative layer would put it behind the section and out of reach of the pointer. `.e-hero__inner` sits above it at `z-index: 1`.
- The control's label and `aria-pressed` follow the element's own `play`/`pause` events rather than the click, because autoplay can be refused (iOS Low Power Mode, a data saver, a browser policy) and the button has to show what actually happened.
- The element sets `muted` as an attribute as well as a property (React only does the latter, and Safari wants the attribute on the element it is asked to autoplay) and carries `disablePictureInPicture`, `disableRemotePlayback` and `controlsList`. A browser that refuses the film tends to paint its own play affordance over it, and the hero already has one control; there should never be two.
- The film pauses when it leaves the screen and resumes when it comes back, but a deliberate pause is remembered in `pausedByUserRef` and survives the round trip. Do not let the observer override it.
- **On a first visit the film is held at its first frame until the opening curtain starts to lift** (`heldByIntroRef`, released by `INTRO_DONE_EVENT` from `src/lib/intro.js`), and the copy rises 0.35s after that so the aperture has cleared the headline first. Before this the film autoplayed under the curtain and the reader joined it 2.6s into a 6.9s loop. `heldAtMount` / `afterIntro` are read into state once, not from the ref, because `react-hooks/refs` rejects a ref read in render; a page reached in-session has no curtain, no hold and no delay.
- Art direction still changes at 760px, but no longer by demoting the media to a band - the portrait encode is cut for that box and renders about 1:1 on a 3x screen. The section becomes a two-row grid: the film and the copy share the first row, and the stat row gets a solid navy band underneath, which is the reference layout. `.e-hero__inner` takes `display: contents` so its two children can hold their own rows; both then carry the shell width themselves. It is a plain div, so dissolving its box costs nothing semantically - do not do this to an element with an implicit ARIA role.
- The phone film row is 394px on a 320x568 and 682px on a 390x844 (the header above it is 65px); the headline needs about 240px of it with the CTA and its padding, so the smallest phone still shows well over a third of the frame above the copy.
- The phone hero carries the headline and `Book appointment`, nothing else. The supporting sentence (`.e-hero__lede`) and the `Call OPD` link are hidden at <= 760px, matching the reference's single-CTA first screen. They are dropped rather than shrunk, and neither is lost to the reader: the same sentence opens the next section, the header keeps the emergency line at the top of every screen, and the drawer's Call OPD is one tap behind the menu button. Both still show from 761px up.
- **The hero owns the first screen at every size**: `min-height: calc(100svh - var(--hd-height))`, with a `vh` fallback line above it, where `--hd-height` is the header at rest from `header.css`. Sized by a share of the viewport it left a strip of the next section's empty top padding showing under the stat band - 43px on a 390x844 phone, 79px on a 1080p monitor - and a blank strip of paper under a navy band read as a gap, not a peek. Measured: `.e-hero` bottom equals `innerHeight` exactly at 320x568, 360x640, 375x667, 390x844, 412x915, 430x932, 360x780, 768x1024, 1024x768, 1440x900, 1920x1080 and 2560x1440. A 1280x600 laptop window is the one that overflows, because the copy needs more than 467px; content is the floor. Verify by measuring, not by eye.
- **On phones the video is `position: absolute` inside its frame.** The section only has a `min-height`, which leaves the grid's block size indefinite and its `1fr` row content-sized - and a 360px-wide portrait video is 480px of content, which held the film row open and pushed the stat band 42px past the fold on a 360x640 phone. Out of flow, the row is exactly what the screen has left and `cover` crops the film to it. The row is `minmax(0, 1fr)` and the frame carries `min-height: 0` for the same reason.
- `Book appointment` is the one thing the phone layout protects and it clears the fold on every size (403px on a 320x568). On phones from 360x640 up the stat band clears it too; `ImpactStats` owns the numbers two sections later regardless.
- `.e-hero__copy` carries 62px of bottom padding on phones purely to leave the corner under the CTA free for the pause control. At 22px the control sat on top of the right end of the action row and stole part of its tap target.
- The control moves to the top right between 761px and 1040px, where the stat row has moved under the copy and the bottom right corner is no longer free.
- Contrast is a requirement, not a preference, and it has to hold across every scene rather than on the poster frame - the atrium skylight and the exam-room floor are near-white. Measure by seeking the film to several timestamps, making the glyphs `color: transparent` while leaving every background behind them painted rather than hiding the copy block (hiding it measures bare film and ignores any scrim or pill the text actually sits on, which once under-reported a measurement by a full 7 points), then sampling each text box and checking against WCAG (3:1 for the headline, 4.5:1 for body-size text).
- Sample each box as a **grid and keep the worst cell**, never as one average. Text sits on moving photography, so a bright patch under a single letter is exactly the failure a box average hides: the phone headline averaged a comfortable 5.40:1 over the same frame where its worst cell was 2.82:1, below the minimum. Worst local cell across six timestamps is now phone headline 4.72:1; desktop headline 4.69:1, lede 11.1:1, call link 15.6:1.
- The phone scrim is deliberately light. The heavy version it replaced was sized for a lede that needed 4.5:1, and once the lede was dropped it was holding nothing but a display line that needs 3:1 - all it did was flatten the lower half of every scene into solid navy, so the hero read as a dark panel with a strip of ceiling rather than as film. The gradient now grounds the last third and leaves the rest of the frame open. If copy is ever added back to the phone hero, the scrim has to be re-measured, not restored from memory.
- The phone CTA is a pill that hugs its label, not a full-bleed bar. The bar was the heaviest object on the screen and read as a slab of white across the frame; the reference lets the film carry the width and gives the action a shape. It stays a generous target at 54px tall with 30px of side padding, which is what matters for the older patients this site is built for - do not shrink it to make it prettier.
- The mobile crop was tested tighter (dropping the empty ceiling) and the tighter version is worse: it truncates the skylight arch mid-curve and crowds the exam room with a foreground stool. Keep the full-height 3:4 cut. The film reads as 70.5% of the phone viewport against the reference's 70%.

`AppointmentPage` reads `branch`, `service` and `name` from the query string so a hospital page, a treatment page or the header can prefill the booking flow.

### ImpactStats

`src/sections/ImpactStats.jsx` is the numbers band directly under the hero and owns the `.e-impact` rules at the end of `src/styles/landing.css`.

- Four cards - surgeries, patients, specialists and hospitals - each with a kicker numeral, a counted figure, a label, a line of copy and a small illustrative panel. The panel is what makes the section feel alive; the layout follows the Function Health "Testing is easy" reference.
- Card copy and the procedure mix / patient trend figures live in `home.impact`. The specialists card is derived from `doctors.json` and the hospitals card from `branches.json`, so neither duplicates content that already exists.
- The heading is the Gujarati line `impact.titleGujarati` over the English tagline (`impact.tagline` plus the accented `impact.taglineAccent`). Gujarati needs its own family - `--e-gujarati` (Noto Serif Gujarati, loaded in `index.html`) - because Inter Tight has no Gujarati coverage and the system fallback differs on every platform. The serif face is deliberate: it pairs with the Source Serif italic tagline and the hero's serif accent, where a grotesque read flat.
- `index.html` loads Source Serif 4 with its italic axis, so the tagline and the hero accent get true italics instead of browser-slanted romans.
- `.e-head__body` caps its measure at `46ch`, which is computed on 16px body text and is far too narrow for a 3.3rem display line; `.e-impact` clears that cap on the head and puts the measure on the tagline instead.
- Each card owns its own in-view trigger (`useInView` on the card, `amount: 0.45`) and passes it down to `CountUp` and to its panel. Do not move the trigger back onto the number itself: on a phone the figure sits near the top of a ~500px card, so watching the figure started the count while only the card's top edge had crossed the fold, and the count finished before the card was readable.
- The figures animate with `src/components/CountUp.jsx`, which counts when its `start` prop turns true and renders the final value immediately under `prefers-reduced-motion`. Numbers are grouped with `en-IN` (1,00,000), so keep values as plain numbers in JSON.
- The hospitals card cycles a highlighted branch chip every 1.9s; the cycle is disabled under reduced motion, and each chip links to `/branches?branch=<slug>`.
- Grid is 4 columns, 2 columns at <= 1080px and **2 columns again at <= 620px, never 1**. Stacked, the band measured 2067px on every phone - 2.45 screens on a 390x844 and 3.8 on a 320x568 - for four numbers, which is where a reader stops scrolling. Two columns put all four figures on one screen (1110px at 390px, 1241px at 320px, head and actions included). The illustrative panels stretch (`flex: 1`) so their tops line up inside a row.
- **On phones the two big counts keep their charts and the two small ones drop theirs.** Four bars and a sparkline read fine in a half column; a list of three doctors or six city chips in a 140px column does not, and both lists are already on the page - the doctor rail two sections down carries the same people with photographs, and the footer lists every hospital. The card carries `data-visual` so the CSS can pick them out (`[data-visual="people"]`, `[data-visual="branches"]`); the components still mount, which is deliberate - the same JSX serves every width.
- The phone mix rows stack the name over the bar and share. Name and share on one row cut the name to `LASIK & refra...`, and truncation is not how this site makes room - `overflow: visible; white-space: normal` on the name at that width, and every name reads whole down to 320px.
- The figure is fluid on phones (`clamp(1.5rem, 7.8vw, 2.1rem)`): `4,52,902+` is the widest thing in the card and measures 98px in a 109px column at 320px and 118px in 144px at 390px. Re-measure if a value grows a digit.

**The wheel (>= 1024px).**

- A rounded paper panel holding a counter (`05 / 11`), an up chevron, a five-slot drum and a down chevron; the stage beside it stretches to the drum's height, so the photograph's frame is always exactly as tall as the wheel (520px). `--cond-item` (76px) in the CSS **must equal `ITEM_HEIGHT` in the component**: the drum's height and its padding are built from it there, and the roll offset here.
- **The names are translated by a spring, never scrolled.** The list is a `motion.div` with `y` bound to a motion value; a click, a chevron, `ArrowUp`/`ArrowDown`/`Home`/`End` animate it to `-index * ITEM_HEIGHT`. It was deliberately not built as a scroll-snap container or a wheel-event handler: a native vertical scroller inside the page captures the reader's wheel on the way past and is a scroll trap by another name, and a `drag="y"` sets `touch-action` so a tablet could not scroll the page over a 500px panel. Nothing here jacks the page's scroll.
- **Each name's distance from the centre slot is written straight to the DOM every frame** (`--d`, in slots, from `useMotionValueEvent`), and the CSS turns it into scale (1.14 at the centre) and fade (floor 0.62), so the drum moves as one and never re-renders to do it. **The first paint is explicit** - a motion value that does not change fires no change event, and without `paint(offset.get())` in the effect every name sat at `--d` 0, the chosen size, until the first roll; that is exactly how the first build shipped.
- **The drum rolls into place the first time it is seen** (`ARRIVE_SLOTS`, 1.5 slots down, released by `useInView` on the panel): the one unasked-for move here, and what tells the reader this is a wheel and not a list. Above the fold it holds, so the roll is not spent unseen.

Both fixes are needed: `clip` cannot be scrolled programmatically at all.

- **The stage never goes blank.** Every photograph asked for stays mounted, stacked; the component names one `on` (fading in over whatever was there, 620ms, and settling from 1.06 to 1 over 1.4s - one slow move, once), one `under` (the previous one, held at full opacity with no transition) and the rest `off`. The fade only starts once the file has decoded (`data-loaded` from `onLoad`, with a `complete` check in the ref callback for a cached file), so a slow image never shows half-painted: verified on a throttled network, `under` at 1 while `on` arrives. The tab panel is `aria-labelledby` the chosen tab, and the button carries a visually hidden `: <service>` so eleven `Know more` buttons are not eleven identical names to a screen reader.
- Contrast on the floor is pixel-sampled worst cell across **all eleven photographs**, with the glyphs made transparent and the text composited over each cell: at 1440px the eyebrow 5.4:1, headline 9.6:1, sentence 9.6:1; on a 390px phone the name 5.6:1 and headline 8.5:1. Re-measure if the gradient, the padding or a photograph changes.

### PatientStories

`src/sections/PatientStories.jsx` is the moving wall of patient quotes directly under the doctor rail and owns the `.e-voices` rules in `src/styles/landing.css`. It replaced a static two-column grid of the same quotes that sat near the bottom of the page.

- It sits immediately after `DoctorHighlights` on purpose: the reader has just been shown who the doctors are, and the next question is what it was like to be treated by them. That is also why it is the one dark band in the upper half of the page - it separates two paper sections and gives the quotes their own room.
- Section copy lives in `home.voices` (`eyebrow`, `title`, `lede`, `note`); the quotes come from `testimonials.json` and nothing is duplicated between the two.
- The head is the page's ordinary `.e-head` label/body grid rather than the centred serif head of `DoctorHighlights` above it. Two centred serif heads back to back read as one long title block. The `note` sits under the eyebrow in the label column, which is otherwise empty on desktop.
- The eyebrow is text, not a number. Renumbering `01`-`09` across the page to slot a tenth section in was churn with nothing to show for it, and the three sections above this one already carry text eyebrows.

**Three behaviours, one per device and preference.** `mode` is chosen in JS - `static` under `prefers-reduced-motion`, `step` on a phone (`matchMedia` at the same 760px the rest of the page breaks at), `drift` everywhere else - and is set on both `.e-voices__rows` and each row so the CSS can follow it.

- `drift` is the continuous marquee: two rows, opposite directions, a duplicated card set inside a track that translates by exactly one set. No JS ticker and no carousel library.
- `step` is a phone-only self-advancing snap rail: it holds a card still for `PHONE_HOLD_MS` (5s), advances exactly one card, and stays swipeable throughout. **A phone cannot use the drift.** One card fills the width there, so a whole card was readable for about half a second in every ten - the rest of the time the reader was looking at a quote clipped mid-sentence at both ends. This is the section's central compromise; do not "simplify" the phone back onto the marquee.
- `static` drops the movement, renders one card set, and hides the control. Same quotes, swipeable, nothing moving.
- The rail wrap is silent: `step` keeps the duplicate set, so reaching the end of the first set is a `scrollLeft -= setWidth` correction onto identical content rather than a smooth whip back across eight cards.

**The rest of the mechanics.**

- The drift keyframe ends at `calc(-50% - var(--voices-gap) / 2)`, not at `-50%`: the track holds two sets and `2n - 1` gaps, so `-50%` alone lands half a gap short and the join shows as a stutter once per cycle. Measured seam error is 0px at 390px, 1440px, 1920px and 2560px; re-measure if the gap or the card count changes.
- Both rows carry **every** quote rather than half each. A set narrower than the viewport opens a gap at the trailing edge - four cards is about 1480px, fine at 1280px and broken at 1920px. Eight cards is 2938px and clears a 2560px monitor. The second row starts halfway through the list and runs `SECOND_ROW_SCALE` slower, which is what stops the two rows drifting as a fixed pair.
- One row on a phone so the section stays a single band of the screen, two from 761px up where a lone row leaves the width looking empty.
- The second card set carries `aria-hidden`, so each quote reaches a screen reader once.
- Motion is stoppable three ways, because moving text that runs for more than five seconds has to be: the `Pause quotes` control, `:hover` / `:focus-within` on the wall, and a `pointerdown` hold. The hold is what covers touch - a finger gets no hover - and on the `step` rail it also keeps the rail from advancing out from under a swipe.
- Cards drift at about 42px a second (`SECONDS_PER_CARD` is seconds per card width). Do not speed either mode up to make the section feel livelier; the phone hold in particular is sized for a 17-word quote read by an older patient.

**Card anatomy and contrast.**

- The theme chip leads the card and the branch closes it. On a wall that moves the reader picks what to read from the tag, then commits to the quote; the branch answers a different question and gets a sentence-case 0.85rem line with a pin, not a second tracked uppercase label competing with the chip at the opposite corner - which is what the first build had.

- Contrast is measured, not assumed. Cards are white: quote (`--e-ink`) 17:1, branch line (`--e-ink-2`) 7.6:1, theme chip (`--e-navy-2` on `--color-clinical`) 8.9:1. `--e-ink-3` is 2.9:1 on white and is used only for the pin glyph beside the branch text. - Edge fades belong to `drift` only. A rail snaps to whole cards, so the only thing left to fade would be the card the reader is reading.
- `--voices-gap` is 16px at <= 720px, equal to the rail's inset: a 14px gap left a 2px sliver of the previous card at the screen edge after every snap.

- It replaced the plain `e-link` that used to sit at the end of each page - `.ab-values__next` on vision, and a link inside the timeline's closing stop on journey. A link buried in the last frame of a pinned film is not a page ending.

### Our journey

`AboutJourneyPage` is the page head and the switch; the timeline is `src/sections/JourneyTimeline.jsx`, which owns the `.ab-time`, `.ab-stage` and `.ab-rail` rules in `about.css`.

**The page around it.** The paper opening carries the page's identity - eyebrow, headline, lede, the founding date set in the serif, and `AboutSwitch`. The stage then opens on its own **title card** (`.ab-time__intro`): the milestones label, `milestonesTitle` in display serif, the lede and a scroll cue, on the navy. That card is what bridges paper into film - the section head used to sit on paper above the stage, which meant the page stacked two blocks of dark-on-white text in front of a dark stage and read flat. The card is deliberately **flat navy with no glow of its own**: the pinned frame below carries the stage lighting, and giving the card a second gradient drew a visible line across the join. The page then closes on `AboutNext`.

**It is a pinned stage, not a list.** The stage is six screens tall, the frame inside it is `position: sticky` for that whole height, and scroll progress across the stage is what plays the stops. The reader scrolls normally and travels through the years. **Nothing jacks the scroll** - there is no wheel handler, no scroll hijack and no fixed positioning; take the sticky frame away and the page still scrolls at its own speed.

Milestones come from `about.journey.milestones`; the closing `now` stop is the only one whose figures are computed - years from `journey.establishedYear`, hospitals from `branches.json`, specialists from `doctors.json` - so the count of hospitals can never contradict the rest of the site. The two are flattened into one `stops` array, so the rail, the paint loop and the list all index the same thing.

**The four things that move.**

1. **The photograph wipes open** behind a travelling accent line (`.ab-stage__sweep`) and holds a slow Ken Burns push from 1.16 to 1.
2. **The year rolls.** `YearRoll` is a digit odometer: one column per digit over a strip of 0-9, shifted by exactly one line, each column a beat behind the last. It rolls from the previous stop's year to this one, so 1995 to 2009 visibly turns three digits. A label that is not a plain number - the closing `Today` - is set as a word instead, and `.ab-stage__odo-a11y` carries the year for screen readers because the digit strips are `aria-hidden`.
3. **The same year again, oversized and outlined**, drifts behind the stop (`.ab-stage__ghost`). It rolls with the foreground one, which is what gives the stage depth.
4. **The rail is a film scrubber**, not a menu: the playhead travels it as the reader scrolls, the ticks behind fill in, and any tick jumps to that stop.

**The timings are deliberately asymmetric, and the reason matters.** The outgoing photograph dissolves over the tail of its own segment and is gone exactly as the next one starts to wipe open, so the frame is never empty and two photographs are never mixed. The copy is a beat behind the picture at both ends, which is what stops one stop's paragraph being read on top of the next one's. The constants at the top of the file are shares of a segment; change them together, not one at a time.

**The paint loop writes styles to the DOM directly, and must keep doing so.** Scroll-linked values handed to a `style` prop get promoted to WAAPI animations by framer-motion, and a stop whose segment starts at progress 0 was mishandled there: the opening stop faded *up* across the whole stage instead of out at the end of its own segment, so two stops were legible at once and the ghost year of 1993 sat behind 2009. Measured, not guessed - `getAnimations()` on the stop returned an `Animation` with the segment's own keyframes, and computed opacity disagreed with the inline value. Six property writes per stop per frame is the fix; do not move these back onto motion values. framer is still used for the odometer springs, which are discrete and fine.

**Three traps that cost real debugging.**

- **A stop still ahead must have its frame hidden, not just its photograph clipped.** All six sit in one grid cell; a clipped `.ab-stage__frame` stops the picture, but `.ab-stage__media` keeps painting its own panel and drop shadow over whatever is playing. Six shadows were stacking over the live stop.
- **The stops are top-aligned, never centred.** Their copy runs to different lengths, so centring each one inside the shared cell parked the photograph at a different height and the frame jumped between stops - measured at 99px, 147px and 161px for three different stops on one phone.
- **Below 520px of viewport height the stage unpins itself** (`SHORT_VIEWPORT`, checked with `useSyncExternalStore`). A phone held sideways has no height for a photograph, a year and a paragraph at once - it overflowed the pinned frame by 49px - so it falls back to the stacked article, which is also exactly what `prefers-reduced-motion` gets.

**The unpinned fallback is the same DOM, not a second design.** `data-mode="static"` un-sticks the frame, stacks the stops, drops the ghost year and the sweep, and pins the rail to the bottom of the viewport as a jump nav. In that mode the active stop comes from an `IntersectionObserver` on a band across the viewport middle rather than from scroll progress, because there are no segments to divide, and a rail jump is `scrollIntoView` on the stop's own id rather than a scroll offset.

**The sticky rail carries `z-index: 2`, and it has to.** The stops' photograph and copy sit at `z-index: 1`, so without it the next stop's photograph painted straight over the jump nav - on a reduced-motion phone and on every phone held sideways the rail was there, at the bottom of the screen, and entirely invisible. It also sits at `bottom: 0` with its own padding and the safe-area inset, rather than 14px above the edge with a strip of stage showing under it.

**Layout and measurement.**

- Two columns from 1024px - photograph left, copy right - and one column below it, photograph over copy. Photographs are 4:3, cropped into `public/assets/media/journey` from the existing `page-headers` and `gallery` assets, 33-119KB each; the hospital's own files are landscape and a portrait crop of a 770x460 source is 345px wide and unusable.
- **None of the six photographs shows the hospital it describes.** Replace them with the hospital's own photography of Visnagar, the theatre and the Odhav building when it exists; nothing in the CSS needs to change when they land.
- Every stop must fit inside the pinned frame at every size. Measure `.ab-stage__stops` against the pin height minus the rail before adding anything to a stop - the slack is 198px on a 390x844 phone and 54px on a 360x640 one, and the `now` stop with its three figures and its link is always the tallest.
- Contrast on the navy, measured: the title and metric 14.3:1, body 10.9:1, the accent tag 7.5:1, the counter, the figure labels and the rail's inactive years 7.0:1. The ghost year is a 0.13 stroke and carries no information.
- Measured with no page overflow, no target under 24px and no target under 44px on the rail, at 320, 360, 390, 414, 820, 844 landscape, 1280 and 1920px, in both modes. Re-measured for the phone pass: every stop fits its pinned frame with slack to spare at 320x568 (19px), 360x640 (50), 375x667 (60), 360x780 (84), 390x844 (121), 412x915 (148) and 430x932 (154), no target under 44px on either About page, and the static rail follows the reader (active stop 2009 after scrolling to the third stop) under reduced motion and at 844x390 and 740x360 landscape.

### Vision and mission

`AboutVisionPage` is the opening, the two statements, the core values and the closing plate. The statements are their own section, `src/sections/VisionStatements.jsx`.

**The two statements are the hospital's own approved words and are quoted verbatim.** They are not paraphrased, shortened or split; the only editorial decision on the page is which phrase in each one carries the promise.

- That phrase is named by `highlight`, a substring of `text`, and is lifted into the accent serif italic. A `highlight` that does not appear in its sentence is ignored rather than dropped or duplicated, so re-wording a statement can never silently lose part of it.
- The emphasis is **colour and italic only, never an underline or a highlight bar**: these sentences run to six lines and more, and a background rule drawn under an inline element breaks at every line box.
- They are full-width editorial rows, not a two-up grid. The mission is 380 characters, and half a shell is not a measure that can carry that at display size - it ran to eleven lines with a third of the row empty beside it. The measure is capped at `48ch` and the marker column uses the same `3fr / 9fr` proportions as `.e-head`, so the statements line up with the section head above them.
- Below 900px the marker becomes a row above the statement (icon, index, kind) rather than a column beside it: a 3fr label column is about 90px there, narrower than the icon itself.

**The six core values are derived from those two sentences and nothing else** - only what you truly need, affordability, a patient-first culture, evidence and modern technology, one standard everywhere, always learning. `Old case file promise` from the earlier version of this page is gone: it is a real hospital promise and it still has a tile in `WhyChooseUs` on the landing page, but it is not in the approved statements and these six have to be derivable from them.

`src/sections/VisionValues.jsx` renders them as a **ruled ledger, not a grid of cards**. Six cards were six separate objects that said nothing about each other; six numbered rows on hairlines read as one ordered set of rules and scan down a single edge.

- **There is no icon, and that is the point.** Six lucide glyphs in six rings were decoration repeated six times, and they made the section read like a template rather than an institution - the same mistake the hospitals menu made with six `MapPin` tiles and the drawer made with a chevron on every nav row, both since removed for the same reason. The serif numeral is the row's only marker, set at display size, and the copy gets the width back. `vision.values` therefore carries no `icon` field; `VisionStatements` still uses icons, because there are two of them and they are not repeated.
- **Each rule quotes the fragment it comes from.** `source` is an exact substring of the mission or the vision and `sourceKind` names which, set in the accent serif italic the statements use for their own key phrases. That is what makes "quoted from the mission or the vision above" something a reader can check rather than something the page asserts, and it ties the two sections into one argument. **If a statement is ever re-worded, re-check every `source`** - the fragments are verified by hand, not at runtime.
- **The reader's row lights up, and that state comes from scroll position as well as `:hover`.** Hover does not exist on a touch screen, and the section would otherwise be inert on the device most patients use. An `IntersectionObserver` on a thin band across the middle of the viewport marks one row at a time; the mark is the accent drawn across that row's top rule, the same device the timeline's playhead uses. The rows are content, not controls, so nothing here is focusable and no tap target was added.
- The row shape is identical at every width - number, title, quoted fragment, sentence, always in that order. Only the wrapping changes: four columns from 1024px, and below that the quote and the sentence drop under the title. `.ab-values__lead` takes `display: contents` there so its two children can hold their own rows; it is a plain div, so dissolving its box costs nothing semantically - do not do this to an element with an implicit ARIA role.
- Below 560px both the quote and the sentence go full width. Indented under the title they would have about 190px of measure on a 320px phone. The type never shrinks with the frame.
- The cards carry no figures - `ImpactStats` on the landing page owns the numbers.
- A decorative `01`-`06` numeral was dropped from the old cards for measuring 2.9:1 (`--e-ink-3` on paper). It earns its place in the ledger because it is now the row's only marker and the rows are an ordered list a reader can count and refer back to, but it is `--e-ink-2` (7.8:1), and `--e-accent` (5.8:1) on the active row - never `--e-ink-3`.
- Rows align on the **baseline**, not the centre: the numeral, the title and the sentence sit on one line across the row, which is what stops six rows from reading as six loose blocks.

**The opening's promise stamp is the sibling of the journey page's founding date** - same block, same micro-label-over-serif treatment. There it dates the hospital; here it names the three words the vision rests on (`vision.promise`). Without it the lede row is half empty on a laptop, and the two About pages stop looking like a pair.

**Contrast on this page is measured, not assumed.** On the navy: the statements and their kind labels 14.3:1, the accent phrase 7.5:1, the notes 7.7:1, the statement index 6.1:1. On paper: value titles 18.2:1, value copy, the source label and the idle index 7.8:1, the quoted fragment 6.4:1 and 5.8:1 on the active row's tint, the promise stamp's label 7.8:1 and its words 18.2:1. One fix came out of measuring - the statement index was `rgba(255,255,255,0.42)` at 3.3:1, under the 4.5:1 that 0.78rem semibold needs, and moved to 0.6.

Measured with no page overflow and no target under 24px at 320, 360, 390, 414, 560, 768, 820, 1024, 1280, 1440, 1920 and 2560px, in both motion modes.

## Services

`/services` is an **index, not a manual**. It shows the eleven services the hospital offers and routes a reader to the right one as fast as possible; what a procedure involves, what to expect and the questions patients ask all stay on `/services/:slug`.

**Eleven is the number that drives every decision on this page.** The build before it carried six services as photograph cards, and that shape does not survive the jump: eleven picture cards is a wall a reader gives up on. The index is a ruled ledger instead, and the result is that eleven services now occupy *less* phone height than six cards did - 1980px against 2894px.

- All copy lives in `services.json` under `page` and is read through `src/lib/servicesData.js` (`servicePage`). The page is `src/pages/ServicesPage.jsx`, the sections are `ServiceExplorer`, `ServicePathway` and `ServiceEmergency`, and all four own `src/styles/services.css` (`.sv-`).
- It is built in the **`.e-*` design system** like the two About pages, and `services.css` only adds what those do not cover. Nothing here restyles a shared primitive.
- **Four sections, one job each:** who we are (the opening), which service is yours (the explorer), what happens when you arrive (the pathway), and what must not wait (the urgent band). The urgent band is last because it is the exception to everything above it - all of that can wait for an appointment and it cannot.
- The footer carries the appointment CTA on every page, so this page does not render `CTASection`.
- It deliberately carries **no branch cards**. The footer lists all six branches on every page and `/branches` is one nav click away; a third listing here would repeat the landing page's old mistake of introducing the branches three times.

### ServiceExplorer

`src/sections/ServiceExplorer.jsx` is the whole middle of the page: three routes into one list, and the list itself.

**It was two sections and became one.** A finder rendered its own answer card, and an index a thousand pixels below rendered a second card for the same services - so a reader met the same object twice and had to work out which one was the answer. Merging them removed a redundant component, took the page from 6322px to roughly 5900px, and turned two parallel tools into one instrument.

- **Three routes, one list:** `page.finder.modes` is `notice` (13 symptom chips), `part` (the eye diagram) and `kind` (the five categories). Every route narrows the same list underneath. Whatever the reader picks, the answer is the list.
- **One narrowing at a time.** Choosing in any route clears the other two, and switching route clears everything. Three filters that stack would need explaining; three that replace each other never do.
- **The status line is not decoration.** `Showing 3 of 11`, the criterion in teal, and a Clear button. Without it a narrowed list just looks like a short list, and the reader has no way back.
- Thirteen concern chips, each naming a service by slug: **every one of the eleven services has at least one chip**, so no service is reachable only by already knowing its name. Seven eye parts, each mapping to one or two services; `emergency-eye-care` is deliberately reachable from neither, because it has its own band and must never be something a reader arrives at by browsing anatomy.
- The controls sit on **one raised card** (`.sv-console`) with the routes as a tab bar, the inputs in the body, and the medical note on a `--color-clinical` strip at the foot. Loose on the page the three routes read as three unrelated rows of chips; grouped, they read as one instrument with a switch.
- **The switch is a self-contained pill group in its own padded head** (`.sv-console__head`), not a full-bleed tinted band. Two earlier shapes were both wrong: stretched across the card each tab was ~570px and the filled pill read as a slab; hugging their labels *on a full-width strip* left two thirds of that row visibly empty. A pill group that is only as wide as its tabs is neither - it fills 42% of the head on desktop and 87-91% on a phone, and looks deliberate at both.
- **Each tab carries two labels and CSS picks one**, the same way the cookie sheet carries `body` / `bodyShort`. The full labels cannot share a phone row; `shortLabel` (`Symptoms` / `Eye part` / `Care type`) fits three across in one row, where stacking three full labels one per row cost most of the first screen before a single chip was visible. Type eases to 0.8rem below 360px rather than a label wrapping - a tab that wraps to two lines breaks the row's height. Measured: no tab label wraps at 320-1920px, tabs stay 46px tall.
- **Below 900px the thirteen chips are a two-row horizontal rail under the readout, grouped under their headings, not a column of rows.** The rows were the build before this one: uniform, tidy, and 880px of card between the readout and the list, so a tap on a symptom narrowed a list a full screen below and the reader scrolled down to see what happened and back up to try another - which is the whole complaint against a phone that gets the desktop stacked. The rail is the shape every catalogue app gives a long option set (a music app's genres, a booking app's categories): the groups are the rail's columns and inside each the chips flow down then across (`grid-auto-flow: column`, two rows), so a group of four is two columns of two and the reading order is untouched. It is 125px tall, the console is 474-497px on every phone (was 1228), and the chip that narrowed the list and the list it narrowed share one screen. **Every cell is the same width, and the width is computed, not chosen.** The first build sized each column to its widest chip and let the rail bleed under the card's rounded border with a 14px fade: on a real phone that was a ragged row of pills with one cut mid-word (`Less dependence on glass`) at the card's edge, which is exactly what got the page sent back. Now `--sv-cell` is derived from the rail's own box - the shell (`100vw - 34px` below 721px, `- 50px` above, less the card's 2px of border), less the rail's two paddings and one gap, halved - so two columns fill the screen exactly and the third begins inside the fade, capped at 200px so a tablet shows three and a half columns rather than two bloated ones. **Below 381px the cell is 70% of the rail**: two cells cannot both hold a label at a readable size there, so the reader sees one column and most of the next. The rail's end padding *is* the fade's width (`--sv-fade`, 36px), so the last column stops before the fade and is never dimmed at the end of the rail. **A label may take two lines and never three** (`.sv-notice .sv-chip--symptom` at 0.84rem - the `.sv-chip` 460px rule sits later in the file and wins on equal specificity, which is why the selector carries `.sv-notice`), and the chosen chip's check sits at the right end over reserved padding rather than pushing the text along as it does on a wide screen: in a fixed cell that push re-wrapped a two-line label to three when chosen. **Each chip carries two labels and CSS picks one** (`shortLabel`, the mode tabs' device): `Blurred or hazy vision` in the rail, and the full sentence in the readout, the criterion chip and the desktop wrap - a sentence is a chip wider than the screen. Three short labels were rewritten after measuring (`Freedom from glasses`, `Eyelid droop or lump`, `Rising eye number`) because `dependence` and `drooping` are single words wider than half a cell. Measured with `Range.getClientRects()`: no short label exceeds two lines at 320, 360, 375, 390, 412, 430, 600, 768 or 844px. Verified with real touch events at 390x844: a horizontal drag moves the rail and leaves `scrollY` where it was; a vertical drag over the rail scrolls the page and leaves the rail; a tap on a chip changes the chart, the count and the list with no page scroll at all. **Chrome only scrolls a focused element into view when none of it is visible**, so a keyboard reader tabbing along the rail landed on a chip half under the card's edge; `revealInRail()` calls `scrollIntoView` with `nearest` on both axes from `onFocus` on the chips and the kind cards, and a Tab walk now lands every one of the thirteen inside the rail with its visual on the chart.
- The symptoms route's hint carries two strings and CSS picks one **on the pointer, not the width**: `sceneHint` (`Hover or tap...`) and `sceneHintTouch` (`Tap...`), swapped under `@media (hover: none)`. A phone has no hover, and a hint that offers one reads as written for a different device; a tablet with a mouse hovers whatever its width, which is why this one is not keyed on 760px. It sits in the chart's own caption while nothing is shown - where the eye is - not at the foot of the list, where it was once buried under thirteen rows. Verified: touch emulation shows the tap line, a desktop the full one.
- **The chips are grouped under four short headings** (`page.finder.groups`: what you see / your eyes and health / for your child / everyday). Thirteen sentences in one run read as a wall a hesitant reader skips; four lists of two to four do not, and the grouping is the first thing a reader uses to find their own line.
- **The route content slides the way the pill travels.** `direction` is set from the tab order on every switch and fed to the three route blocks as a framer `custom` value, so moving from symptoms to the eye slides the content left and coming back slides it right - a switch reads as moving along a row of three rather than swapping a card. Under `prefers-reduced-motion` the variants collapse to opacity only.
- **Route three is category cards, not chips.** Five chips in an otherwise empty card while the other two routes had a picture to look at was the section's weakest moment. Each `.sv-kind` card now lists the services it contains with their global numbers, so a reader sees what "Specialty clinics" holds before spending a tap on it. `auto-fit, minmax(210px, 1fr)`: three at 768px, five from 1280px. **On a phone (<= 640px) the five cards are a swipe rail** (`grid-auto-flow: column`, `min(74vw, 300px)` a card, `scroll-snap-type: x mandatory`, the same bleed as the symptoms rail): one card and the edge of the next in view, the route 355px tall instead of the 911px five stacked cards cost. No card label wraps at any width. Verified with real touch: a drag moves the rail only, and a tap on `Children and squint` narrows the list to three tiles with no page scroll.
- **Both visual routes sit in the same well.** The chart's frame and the eye's `.sv-parts__frame` share one treatment - a soft clinical tint with an inset edge - so the two read as one instrument with two displays rather than two unrelated pictures. The sclera and the chart both read better against the tint than against bare white.
- The console carries **one ornament**: a 3px rule along its top edge, navy through teal to accent. It is what tips a white rectangle over into reading as an instrument, and it is the only decoration the card has.
- **A chosen chip grows a check at its left edge and makes room for it** (`::before`, scale 0 to 1 with a 60ms lead, padding-left 18px to 32px). Choosing reads as a small confirmation rather than a colour flip. Verified: the check goes from scale 0 to 1 at 45 degrees on selection.
- **The readout's figures are set in the serif at 1.55rem** (`.sv-status__num`). The sentence stays in the JSON; `statusParts` splits the template at its `{count}` / `{total}` tokens so the numbers get their own element without the copy leaving the data file. The criterion is a teal chip on a 0.06 tint - 0.08 measured 4.95:1 for a 14px semibold, a pass with no margin; 0.06 measures 5.11:1.
- The filled pill is **one element that travels** between tabs (framer `layoutId`), not a background that blinks off one and on to the other. Because it is a separate absolutely positioned element, a contrast walker reading computed styles sees the button as transparent and reports 1:1; pixel-sampled, the selected label is **14.27:1** on the navy.

**Nothing here navigates or filters on its own, and that rule was learned three times.**

1. The first build **scrolled the page to the index** the moment a chip was picked, which stole the answer out from under the reader and made the answer card pointless.
2. The diagram's `onMouseEnter` was wired to the **same handler as its click**, so a mouse crossing the eye sent the reader to a service page.
3. After the merge, hover and choice **shared one piece of state**, so a mouse crossing the eye silently re-filtered the list - the same fault one level down.

So preview and choice are separate state (`previewPart` / `part`), `EyeDiagram` takes separate `onPreviewPart` and `onChoosePart` props even though they do similar things, and the filter reads the chosen value only. **Hover previews, click chooses, and only a link the reader presses leaves the section.** Verified: hovering all seven regions leaves the list at 11 rows and changes no route, at 1440px and 390px.

**The one exception is revealing the results, which is the opposite of navigating away from them.** Where the list sits beside the controls there is nothing to do. Stacked on a phone it lands below the whole console, so a reader chooses and sees nothing happen; `revealResults()` scrolls with `block: "nearest"` **only when less than 240px of the results is visible**. Measured: 0px at 1440px, ~450px at 390px, 0px on every hover.

**The list and its pane.**

- **The list is read in runs under a heading, not as eleven equal rows.** The source order is already grouped by kind of care, so `groups` splits `shown` into consecutive runs and each run gets its category once as a `.sv-group__head` (label plus count); the rows under it carry only their own name. The per-row category label this replaced was the same two words printed on every row of a run. Narrowing keeps the shape - two surgical answers still sit under `Surgical care`, and a symptom's single answer sits under its own heading, which tells the reader what kind of care it is. The scroll observer therefore watches `.sv-row` elements, not the list's direct children.
- **The number is global and permanent.** `getNumberedServices()` numbers the source list once, so "07" is the Myopia Clinic whether the reader is looking at all eleven or at the three children's services. Renumbering per filter would make one service two different things.
- Rows animate with framer `layout` inside `AnimatePresence`, so narrowing visibly collapses the list rather than swapping one set of text for another. The active row's title steps 3px toward the reader.
- Chips arrive on a short stagger when a route opens and take a `whileTap` scale, and the status figure cross-fades on its own key so a changed count is visible rather than silently different.
- **The untouched diagram breathes an invitation** (`.sv-parts__frame[data-idle]` animating the globe stroke) and **stops the moment a part is chosen**. An invitation must never keep running after it has been taken.
- **On a wide screen the photograph lives in one sticky pane beside the list, not in eleven rows.** Eleven picture cards is a wall; the pane brings the pictures back and the page pays for exactly one. It is `aria-hidden` - every word in it is a copy of the row it mirrors.

### SymptomScene

`src/components/SymptomScene.jsx` is the symptoms route's counterpart to the anatomy drawing. There a patient points at *where* the trouble is; here they recognise *what it looks like*. An eye chart is the one image every patient already associates with eye care, and every symptom degrades it in a recognisable way.

**It is the Snellen chart, redrawn in SVG rather than embedded as an image** - the eight standard rows from the lone E down to `L T I P H`, with the acuity fractions `20/200` to `20/20` in a column on the right, portrait like the one on an examination-room wall. A raster was rejected for three reasons: it would blur under its own effects (the effects *are* blur), it could not be themed, and it would ship bytes for a thing eight lines of text describe exactly. The letters are the site's serif at 700 with a hairline stroke of the same ink (`paint-order: stroke fill`), which squares the serifs off toward the block optotypes of a printed chart without loading a slab face.

- **One chart per route, never one per option.** For a while every symptom row carried its own 60px thumbnail of the chart beside a label and a ring, on the argument that a reader could compare all thirteen at a glance. Measured against the reader instead: at 60px blur, haze, glare and clear all read as the same fuzzy E, so the thumbnails compared nothing, and fourteen charts, thirteen rings and thirteen 72px boxes were what made the route look like a control panel on both a laptop and a phone. The `compact` render path, `E_VIEW` and the `.sv-scene--compact` rules went with them. The large chart is the one preview: it mirrors the hovered or chosen chip, beside the chips on a laptop and pinned at the top of a phone.
- **Effect strengths are variables** (`--sv-blur` and friends on `.sv-scene`), so a smaller reading of the chart - the service detail page's readout - can soften them without touching the component.
- **The options are the console's own `.sv-chip` pills** (`sv-chip--symptom`), the control the eye route's part chips already are, so the two visual routes share one vocabulary: a white pill with the `--sv-edge` boundary, a navy fill that grows a check at its left edge when chosen, a lift on hover and on keyboard preview (`data-preview`). They wrap under their group heading beside the chart from 901px - two or three to a line at 1440px, 499px for all thirteen against a 603px readout, and no label wraps inside a chip from 960px to 2560px - and are full-width rows below (see the explorer). Two earlier shapes were both worse: bare rows with a ring at the far edge left the mark 400px from its label, and two columns of boxed rows at 1180px was a grid of twenty-six objects to read before choosing one.
- **The chart is sized like a chart on a wall, not a poster, and it sits on the well.** At half the console a portrait chart was 1050px tall and ran past the fold; the column is capped at 340px, which fits a laptop screen with the sticky offset and shows all eight rows. `.sv-notice > .sv-scene` carries the same tinted, inset-edged frame `.sv-parts__frame` gives the eye - the chart, its `How it can look` eyebrow, the name and the hint inside one object - so the readout reads as the instrument's display rather than a picture floating beside a list. **The caption carries `min-height: 102px`**, room for the idle eyebrow, `Clear vision` and a two-line hint or for a two-line name, and the hint leaves the layout (`display: none`, not opacity) the moment a symptom is shown; both are what keep the well at exactly 603px in every state, measured, so nothing resizes as the pointer crosses the chips.

- **Hover or tap a chip and the chart shows it.** `visual` on each concern names the effect - `blur`, `haze`, `glare`, `floaters`, `spots`, `tunnel`, `dark`, `double`, `droop`, `clear` - and CSS draws it as a filter on the chart or an overlay above it, so a new concern needs one word in the JSON and nothing in the component. One 480ms transition on the chart is what makes moving between symptoms a morph rather than a swap.
- **The effects are how patients describe their sight, not clinical findings.** Tunnel vision for a family history of glaucoma and floaters for flashes are the standard patient-education images; nothing in this frame may ever read as a diagnosis, and the console's note says so directly beneath it.
- **Preview and choice are separate state here too** (`previewConcern` / `concern`), exactly as for the eye parts. Hover and keyboard focus change the chart; only a click narrows the list. Verified: hovering all thirteen chips shows ten distinct visuals and leaves the list at eleven rows, hovering while a chip is chosen previews without un-narrowing, and moving the pointer off the block returns the chart to clear. **Test that reset with a real pointer** (`Input.dispatchMouseEvent`) - React's `onMouseLeave` is synthesised from `mouseout`, so a raw dispatched `mouseleave` event does nothing and reads as a bug.
- The chart is `aria-hidden` and the chips carry the words. Under `prefers-reduced-motion` the floaters hold still and every effect renders in its finished state.
- **Below 900px the chart is a landscape readout above the chip rail, not a fixture above a list and not dropped.** It is the same well, laid out landscape and full width: a cut of the chart's top rows on the left (`preserveAspectRatio="xMidYMin slice"`) and the words on the right, with the `How it can look` eyebrow above them from 361px up. **While nothing is shown, the hint takes the name's line** (`[data-idle]` hides the label there): a phone has no hover, and `Tap a description to see how people often describe it` is worth more than `Clear vision` under letters that are plainly clear. The moment a chip is tapped its name has the line, in accent. ### EyeDiagram

`src/components/EyeDiagram.jsx` is the cross-section behind the second route: a patient knows *where* the trouble is long before they know what it is called. "The back of my eye" is a thing anyone can point at; "retina" is not.

**It is drawn, not modelled, and that was a deliberate decision rather than a limitation.** Depth here is gradients, specular highlights and layered translucency: a shaded sclera lit from the upper left, a translucent vitreous, a glassy cornea with its own glint, a biconvex lens with a highlight down its face, a cylindrically shaded optic nerve, and a soft contact shadow grounding the globe. That ships zero bytes of dependency, stays crisp at every size, keeps the accent states and the whole thing themeable, and leaves the markup screen-reader safe. **A WebGL model was considered and rejected**: it buys a little more realism for a library of 150KB+, a GPU cost on the phones most patients use, and a canvas with no accessible structure at all - against `Avoid unnecessary large libraries` and a mobile-first brief for older patients. If it is ever revisited, the part chips must remain the real controls.

- **Every shaded body agrees on one light direction** (upper left). That single rule is what stops a set of gradients reading as a set of unrelated blobs; if a new part is added, shade it the same way.
- The globe's sheen, the corneal glint and the lens glint are `pointer-events: none`. They carry no information and the sheen in particular sits directly over two tap targets.
- **The drawing is `aria-hidden` and holds no controls.** The real controls are the part chips beside it - real `<button>`s with `aria-pressed`, all tab-reachable. Pointer events on the SVG are an enhancement on top of those buttons, never the only way in. That is what keeps an interactive picture keyboard-operable without inventing ARIA for it.
- Every region carries an **invisible `.sv-eye__hit` circle far larger than the shape it covers**: a 3px stroke is not a tap target, and this page is read by older patients. Measured smallest hit area is **46px at 320px** and 53-96px everywhere above it.
- `.sv-eye` centres itself with `margin-inline: auto` because `.sv-parts__frame` is `display: contents` - the drawing is a direct grid child, and without it the eye sat hard against the left of a 1140px console. It grows to `min(100%, 540px)`: a 430px eye in that console left the detail too small to be worth drawing. The diagram sits inside the console's padding now, so on the narrowest phones that padding is what squeezes the targets - `.sv-console__body` drops to 14px at <= 420px. **The frame gives way, never the target.**
- **The chosen part comes forward and every other region dims to 0.32.** Dimming the rest is what makes one region readable inside a drawing this dense - highlighting alone was not enough.
- The live region breathes a **`drop-shadow` glow on the region itself**, so the light follows the shape of the anatomy. The first version pulsed a fill on the invisible `.sv-eye__hit` circles and drew two pink discs across the eye. Nothing moves while a region is lit - the drawing has to stay anatomically honest.
- The `viewBox` is cropped to `0 40 520 300` rather than the square it was drawn in. The shapes span y 54-326, and the extra air above and below pushed the part chips and the answer off the screen together.
- A first version was drawn in hairlines on a near-white globe and did not read as an eye at all. Strokes and fills were all strengthened; if the palette changes, check it still reads as an eye at 390px before trusting it.

### IrisMark

### ServicePathway

`src/sections/ServicePathway.jsx` is the navy band: the same six steps - examination, investigations, consultation, treatment plan, treatment, follow-up - whichever service the reader picked. Saying it once here is what stops eleven service pages each repeating it.

### Contrast and measurement

**Measured, not assumed.** Solid-ground text was sampled with a compositing walker; the urgent band was sampled from **real painted pixels**, because its ground is a gradient and computed styles cannot see it.

- On paper: headline and row titles 16.6-18.2:1, serif accent 6.4:1, ledes 7.1-7.8:1, row text and category labels 7.1:1, filter counts 8.1:1, the opening's urgent link 7.7:1. On the navy: heading 14.3:1, step title 14.3:1, step text 8.4:1.
- On the rust gradient, worst local cell across 390, 768 and 1440px: label 8.1-10.1:1, heading 14.0-14.9:1, action label 7.5-8.2:1, action text 9.7-10.4:1, helpline 8.5-8.8:1, warning signs 12.5-14.5:1.
- **Two traps in measuring a gradient band, both of which produced false failures:**
  - `html` carries `scroll-behavior: smooth`, so a rect read straight after `scrollIntoView` is read mid-travel and the sample lands on whatever is really at those coordinates - the footer, in practice. Set `scrollBehavior = 'auto'` first.
  - Read the element's real `color` **before** setting the glyphs transparent. Reading it after returns `rgba(0,0,0,0)` and every ratio comes back as exactly 1:1.
- **Control boundaries need `--sv-edge` (`#7f8b96`), not `--e-rule-2` or `--e-rule`** - the concern chips, part chips, filter chips, the mode group and the answer cards are all controls whose border is the only thing identifying them. `--e-rule-2` measures 1.58:1 and `--e-rule` 1.18:1 against the 3:1 WCAG 1.4.11 wants; `--sv-edge` measures 3.48:1 on white and 3.16:1 on the paper tint. Same edge value the header and cookie sheet use. Do not lighten it. **The answer card caught this late** - the whole card is a `Link`, so its border is a control boundary, not decoration.
- **The explorer's ground is a gradient, so every figure on it is pixel-sampled, worst local cell** - a computed-style walker sees `background-color: transparent` and silently measures against the page behind it. Section eyebrow 7.0:1, heading 16.4:1, lede 7.0:1; tab idle 7.1:1 and selected 14.3:1; chip idle 6.4:1; the console note 9.8:1 on the clinical strip; status figure 16.2:1, the teal criterion 5.6:1, Clear 11.3:1; row number 6.4:1, title 18.2:1, category 7.8:1, text 7.8:1; the availability note 7.0:1; pane category 7.8:1, title 18.2:1, bullet 7.8:1. All eighteen pass.
- **A reveal measured off-screen reads as invisible content, and that is not a bug.** Jumping straight to the bottom of the page leaves the pathway steps and the warning signs at opacity 0 because they were never in view; scrolling to them, or deep-linking `#emergency`, shows them at full opacity. ## One service: /services/:slug

**Five short blocks, and one of them is the page.** A hero, a card the reader explores, the visit, the questions, the way on - and an action bar that follows a phone reader down the screen. On a 390x844 phone the whole page is 2845px: about three and a half screens.

Two builds came before this one and both were too much page:

1. The first gave thin content (two paragraphs, four bullets, two questions) the index's airy label-left / heading-centre head. Every band was two thirds empty and the page read as a well-typeset wireframe.
2. The second filled the width - a full-bleed hero, a navy includes panel, an anatomy band, a team band, a closing band - and ran to **6582px on a phone**, eight screens for one service.

**The fix was not more design, it was less page.** The detail now lives in one tabbed card instead of a stack of full-width bands, and the rule for anything new is: *if something has to go on this page, it goes in a tab.*

- All copy lives in `services.json` - the page's labels under `page.detail`, and each service's own `longDescription`, `causes`, `symptoms`, `featureBullets` and `faq` under `items`. It is read through `src/lib/servicesData.js` (`serviceDetail`).
- The page is `src/pages/ServiceDetailPage.jsx`, the sections are `ServiceHero`, `ServiceExplore`, `ServiceVisit`, `ServiceFaq` and `ServiceRelated`, the two components are `ServiceActions` (the hero's row) and `ServiceActionBar` (the sticky one), and all of them own `src/styles/service-detail.css` (`.sd-`).
- It uses `.e-shell`, `.e-btn` and `.e-link` from the design system but **not `.e-head` or `.e-sec`** - both are built for bands with more copy than this page has. `.sd-head` is a flex row (heading left, one link right) and `.sd-sec` is a tighter band.
- It carries **no branch cards, no doctor rail, and does not re-explain the six steps of a visit**. The footer lists every hospital on every page, `/doctors` owns the consultants, and `ServicePathway` on the index owns the pathway.
- The page it replaced was `PageHeader` plus three `global.css` sections and the old `FAQ.jsx`. All of its rules (`.service-detail*`, `.feature-list`, and the `.e-faq*` block in `landing.css`) are gone, along with `FAQ.jsx`, whose only consumer this was.

### ServiceHero

**Built to the Function Health "What we test" reference**: an editorial head on warm paper, then one wide media card carrying the photograph and a rail of glass chips along its foot. `src/sections/ServiceHero.jsx`.

It replaced a full-bleed navy band with the copy laid *over* the photograph. That band had to fight its own picture for contrast across eleven very different photographs and read as a stock banner. Splitting the two - **words on paper, picture in a frame** - lets the type be set properly and lets the photograph be a photograph.

Four things carry the reference and are the ones most easily lost:

1. **The headline is serif, centred, with its closing word in italic accent.** `splitServiceTitle()` takes that word off the end of the title - every service but Oculoplasty ends on the noun that names the kind of care (Surgery, Care, Services, Clinic, Examination), which is exactly the word the reference italicises. A one-word title keeps the roman face rather than being italicised whole.
2. **The card is a wide letterbox with air around it**, not a band bled to the window: `21/9` from 901px, `3/2` below it, `5/6` below 640px. Those are measured, not chosen - at `21/9` a 390px screen left 103px of visible photograph and a 320px one just 36px once the foot had taken its share. Every width now keeps 166-365px of picture.
3. **The chips are translucent glass over the photograph**, not a list under it - each one a ticked line carrying the service's own `featureBullets`. The reference writes `Included` on every card because its list runs to 160+ tests and inclusion varies; everything shown here is included by definition, so that word was the same noun printed four times under a label that had already said it. The tick carries it.
4. **Four chips share the row from 901px up; below that they are a scroll-snap rail with the next one peeking**, which is what says it can be swiped. Same mechanism as the doctor rail, and the browser's direction lock is what keeps a horizontal swipe out of the page's vertical scroll.

**The chips live here and nowhere else.** `featureBullets` used to be a fourth tab in the explore card (`How we treat it`); that tab is gone, because this is the one element on the page that says what the reader actually gets and saying it twice is what the rest of this page is built to avoid. The tab set is now Overview / Why it happens / Signs to notice.

**Two contrast rules, both learned by measuring:**

- **The glass is dark, not white.** A white translucent panel *raises* the luminance behind white type, and over these eleven photographs - a dark theatre through to a near-white clinic - the tick measured 3.7:1 and the label 2.4:1. `rgba(11, 25, 39, 0.46)` keeps the photograph visible through the chip and makes the type reliable on all of them.
- **The foot carries its own floor**, a local gradient under the label and the chips, rather than relying on the frame's scrim. A wash sized for the brightest photograph would flatten the other ten; a local floor leaves the top of every picture bright and guarantees the ground where the type actually is. Measured worst local cell across all eleven photographs at 1440px and 390px: tag 8.0:1, included label 5.2:1, chip text 15.4:1, chip tick 16.5:1.

The two glass tags at the top left - the kind of care and the part of the eye - are both derived, neither written per service. The actions sit centred under the lede on paper, so `ServiceActions` uses the filled navy button rather than the light one, and the sticky action bar still anchors to that row.

**Below 640px the hero sheds four things, and the count is the argument.** A phone hero was rendering **twenty-one separate pieces of text** before the reader reached any content. `Included` appeared four times, `Bharuch` twice, and the two glass tags say what the reader already knows - the kind of care is how they got here, and the part of the eye is what the first tab below opens on. Call and WhatsApp go too, because the action bar carrying both rises the moment this hero scrolls away. That leaves **eleven**: a back link, the title, the sentence, one button, one label, four chips and one note - one action, one picture, one list. **If something is added back to this hero, take something out.**

### ServiceExplore - the card

Everything a patient wants to know about one service, in one card they explore rather than four bands they scroll past. **Three tabs: Overview, Why it happens, Signs to notice.** `How we treat it` was a fourth; its `featureBullets` are the hero's glass chips now.

- **Tabs are built from what the service actually has.** A routine eye examination and optical services have no `causes`, so that tab is not rendered rather than rendered empty - they show two tabs where the other nine show three.
- **Overview** is the hospital's paragraphs beside `EyeDiagram` with this service's region lit, captioned with the part's name and the finder's own sentence for it. The drawing carries **no handlers** - the part is a fact about this service, not a control. On a phone the drawing goes first: a patient recognises the part of the eye before they read about it. **The `order: -1` sits on the figure's wrapper (`.sd-split__figure`), which is the grid child** - written on `.sd-area` inside it, it did nothing and the prose led on every phone until the audit caught it. Verified: the figure's top is above the prose's at 390px.
- **Signs to notice** is the interactive one. Each symptom is a button; choosing one draws it on the Snellen chart through `SymptomScene`. On a phone the chart leads and the list follows, where a thumb can reach it. The card's foot carries the note that these are descriptions, not a diagnosis.
- Content swaps in the direction the pill travels (framer `custom`), so a switch reads as moving along a row rather than as the page changing underneath. The filled pill is one element that travels (`layoutId`), not a background that blinks off one and on to the next.
- The tab bar is a **scroller, not a wrap**: four labels cannot share a 358px row, and a tab bar that breaks to two lines stops reading as one control. The chosen tab is centred by writing `scrollLeft` on its own scroller, never with `scrollIntoView`, which would scroll the page as well.
- **The card grows and shrinks to the tab rather than snapping to it**, so the page never jumps under the reader's thumb. Two traps, both of which cost a debugging pass:
  - The height is written **straight to the DOM**, not held in state: a state setter here trips `react-hooks/set-state-in-effect`, and the value is a measurement, not something the render depends on.
  - It is a **callback ref, not an effect keyed on the active tab.** `AnimatePresence mode="wait"` holds the outgoing panel until its exit finishes, so an effect that fires when the tab changes measures the panel that is *leaving* - and then its `ResizeObserver` reports zero the moment that panel detaches, collapsing the card to 0px. Measured: with the effect version the frame read 0 on every tab after the first; with the callback ref it tracks each panel exactly (overview 632, causes 251, signs 515, treatment 327 at 390px).
- **Nothing here navigates.** Choosing a sign changes the chart beside it and nothing else; the URL never changes.

### ServiceActionBar

Most people open a hospital website on a phone, often in a waiting room or on the way in, and the thing they want is to book or to call - not to scroll back to the top to find the button.

- It is **`position: sticky; bottom: 0` inside `<main>`, never `position: fixed`.** Sticky means it releases at the end of the page instead of sitting on top of the footer, so it needs no spacer, fights nothing for z-index, and hands the screen back exactly where the footer's own appointment CTA takes over. A fixed bar would also cover the drawer's thumb-zone actions and the cookie sheet. Verified: pinned to the bottom of the viewport mid-page, released above the footer at the end.
- **Phones and small tablets only** (<= 900px). On a desktop the hero's actions are never far, and a bar across the bottom of a wide screen is clutter.
- Below 560px the two quiet actions drop to glyphs and `Book appointment` keeps its words: three full labels cannot share a 358px row at a 48px target.
- On Emergency Eye Care the call action is the helpline and turns red.

### The motion, and the rule it follows

**One thing moves without being asked for - the hero - and everything else answers the reader.** Motion here is orientation and feedback, never decoration, and every piece of it renders finished under `prefers-reduced-motion` (verified: hero at opacity 1 with no transform, the eye lit on the first frame, chain steps, related rows and panel rows all at 1).

- **The hero arrives.** The headline, sentence and actions rise on a 70ms stagger, then the media frame lifts in behind them. Everything lands at opacity 1 with no transform under reduced motion.
- **The action bar rises when the hero's own actions leave the screen** and drops back when they return, so a reader never sees the same button twice. It watches the element (`IntersectionObserver` on the hero's action row, passed down as a ref - React 19 takes `ref` as an ordinary prop) rather than a scroll offset, because the hero is a different height on every service and at every width. Off-screen it is `pointer-events: none; visibility: hidden`, so it can never take a tap or a tab stop while it is out of view.
- **The visit is scrubbed, not stepped through.** The panels swipe with the finger and the rail's travelled portion fills behind them frame by frame; under reduced motion a dot press jumps the rail to the exact step and the active dot loses its scale pop, but the step still changes.
- **The card's contents assemble.** The panel slides in the direction the pill travelled and its rows arrive behind it on a 60ms stagger. Measured mid-flight: the first row at 0.17 while the rest are still at 0, all settled at 1. A tab that assembles reads as a different view of the same card; a tab that appears whole reads as the page having been replaced.
- **The eye lights a beat after the drawing lands** (`LIGHT_UP_MS`, 420ms). `EyeDiagram` mounts with no active part and `AreaFigure` switches it on, so the reader watches the answer arrive instead of being handed it. The regions already carry a 220ms colour transition and the lit one breathes `sv-eye-glow`, so this needs nothing but the delayed switch - and it re-runs on every visit to the tab, because AnimatePresence unmounts the panel it lives in. It is a small top-level component rather than an effect in `ServiceExplore`, which keeps the timer out of the tab logic.
- **The questions glide open** through `::details-content` with `interpolate-size: allow-keywords`, scoped to `.sd-faq__list` rather than `:root` because the property inherits. Pure CSS, no JavaScript, and a browser without support simply snaps open exactly as before - the `<details>` semantics that section exists for are untouched.
- **Everything tappable gives something back**: tabs, sign rows and the hero buttons take a `whileTap` scale, the sign's ring fills and draws a check, related rows lift their thumbnail and lean their arrow toward the page they open.
- The lower sections use the shared `Reveal`, and related rows stagger in on scroll at 70ms apart.

### Contrast and measurement

**Measured, not assumed**, and pixel-sampled worst-local-cell because the hero sits on photography - a computed-style walker sees `background-color: transparent` and silently measures against the page behind it.

- Hero, worst across all eleven photographs: **10.1:1**.
- Everything else at 1440px and 390px, worst: **6.8:1** (the area caption). Headings 18.2:1, labels and body 7.1-7.8:1, tab idle 7.6:1 and selected 14.3:1, chain step 16.4:1, FAQ question 18.2:1 and answer 7.8:1, action bar 14.3:1.
- **Three sampling traps that produce false failures, all artifacts of the tool rather than the page:**
  - **A wrapper with a styled child cannot be sampled.** Making `.sd-visit__note span` transparent left its `<strong>` painted, and the sampler read 1.7:1 off the glyphs it had not hidden. The note's text now has its own element; measure leaf elements only.
  - **A `display: none` element returns no client rects**, and its zero box samples the top-left of the page - which reported the action bar as 1.06:1 at desktop width, where it is correctly hidden. Skip elements with no rects.
  - **Translucent type must be composited against the pixel behind it** before the ratio is computed. Reading `rgba(255,255,255,0.5)` and measuring only its RGB reported every figure on a navy ground as 14.27:1, including several that are not.
- **Control boundaries need `--sd-edge` (`#7f8b96`)**, the same value the header, the cookie sheet and the services index use: 3.48:1 on white against the 3:1 WCAG 1.4.11 wants. `--e-rule-2` is 1.58:1 and belongs between bands only. There is no navy control on this page any more - the `--sd-edge-light` token the navy-hero build carried for one was never read and has been removed; if a control ever sits on a dark ground here, reintroduce it at `rgba(255,255,255,0.46)` and measure.
- Measured with **no page overflow and no target under 24px** at 320, 360, 390, 414, 768, 820, 1024, 1180, 1280, 1440, 1920 and 2560px, across **all eleven services** and the not-found state, in both motion modes, with no console errors on any route. ## Our hospitals: /branches

**One head and one instrument.** A drawn map of Gujarat beside six rows, one per hospital, and the two answer each other. The page's job is to get a reader to the right hospital and, if that is all they need, to its number or its door without another page; each hospital's own page carries everything else, so nothing about a hospital is written twice. The footer carries the appointment CTA, so there is no closing band.

The build before it was three listings of the same six hospitals on one screen - a tab strip, a showcase card with a Google embed, and six dense cards each carrying every desk number, the email, two buttons and the hours - on the old `PageHeader` and about 800 lines of `.branch-*` rules in `global.css`. All of that is gone, with `BranchCards.jsx` and the `page-headers/hospital-corridor.jpg` it was the last consumer of. The page is `src/pages/BranchesPage.jsx`, the section is `src/sections/HospitalFinder.jsx`, the drawing is `src/components/HospitalMap.jsx`, and all three own `src/styles/hospitals.css` (`.hs-`). Copy lives in `branches.index`; each hospital's place on the map is its `map` point in `branches.json`.

### The rows are the controls

- **Each row is the whole way into a hospital**: the name in the serif, the locality, `Head office` where it is true, and the two things a person in the street wants first - `Call OPD` and `Directions` - as pills. The whole row opens the hospital's page through a stretched link (`.hs-row__main::after`) and the pills sit above it (`z-index: 1`); the `View hospital` marker at the right is `aria-hidden` and takes no pointer, because the link is the row. WhatsApp and booking are deliberately not here: the header and the drawer carry both for the chosen hospital, and the hospital page carries them for this one.
- **The lit row is the one the map shows.** On a fine pointer the row under the cursor lights its dot (`previewSlug`), a click on a dot chooses it (`selectedSlug`), and the two are separate state so a mouse crossing the map can never change what the reader chose - the eye diagram's rule. `active = preview ?? selected`. At rest the lit hospital is the one the header has stored for this reader (`getStoredBranch`), so the map and the number at the top of the screen never disagree; `?branch=<slug>` from an old link wins over it and scrolls to its row **two frames later**, because `RouteScrollManager` scrolls every new route to the top on the next frame and would cancel it.
- **Below 1024px the map sticks under the header and the row passing beneath it is the one lit.** `stacked` is read with `useSyncExternalStore` over `matchMedia`, and a rAF-throttled scroll handler reads the boxes rather than an IntersectionObserver band, because the map's own edge moves by the header's height as the header hides and returns (`body:has(.hd--hidden) .hs-map { top: 0 }`, the symptoms readout's device). The reading line is 64px under the map (`READ_LINE`), so the first row is lit the moment the map sticks and each row takes over as it passes - the first version lit the middle of whatever was visible, which on a 390x844 meant the third row lit as soon as the map stuck. It only runs once the map is stuck (`STUCK_AT`), so the stored hospital holds until the reader scrolls.
- **Flex, not grid, for the two columns**: a sticky grid item is confined to its own row and never sticks. The map is `flex: 0 0 clamp(400px, 42%, 540px)` beside the list from 1024px (46% between 1024 and 1179px, where the pills are glyphs and the list needs less), sticky at `top: calc(var(--hd-height) + 20px)`, and full width above the list below that with its height capped at `--hs-map-cap` (`min(40vh, 380px)`, `min(38vh, 300px)` on phones) so the rows keep most of the screen.
- **The row sheds its words before its street wraps.** Beside the map the list is narrower than the page: `View hospital` goes below 1300px and the pill words below 1180px (and below 700px), where the pills are 44px glyph circles with the hospital's name in `aria-label`. Measured with `Range.getClientRects()`: no locality wraps from 1024 to 1920px, and `M.N. College Road, North Gujarat` - the widest at 226px - has 240-244px of column from 1300px up.
- A row is 75px on a 390x844 phone (97px for Visnagar's tag), so **the stuck map and all six rows share one screen** there; six rows are 456px under a 269px map.
- **The phone title is two lines, `Six hospitals` over `across Gujarat`.** With the desktop's `16ch` cap and the accent word forced onto its own line, every phone from 320 to 430px set three lines with `across` stranded alone between them; below 700px the cap lifts and the `em` goes inline. Measured with `Range.getClientRects()`: 2 lines at 320, 360, 375, 390, 412 and 430px, and the list's label reaches the first screen of a 360x640.
- **Below 520px of viewport height the map unpins** (`(max-width: 1023px) and (max-height: 520px)`): a phone held sideways has no height for a stuck map and the rows under it - at 844x390 the map was a 156px drawing marooned in an 844px navy card that never left the screen, with the status detail line back across it. There it is a plain card at the top, `width: fit-content` around a 62vh drawing, the detail line dropped as on a phone, and the rows are the controls - the same call `JourneyTimeline` makes when it unpins its stage.

### The map

- **It is a sketch of Gujarat, not an embed.** A simplified outline (`OUTLINE`, projected once from ~45 coastline and border points and Catmull-Rom smoothed - Kutch, the two gulfs, Saurashtra, the eastern border), a dashed route threading the six hospitals north to south, a dot per hospital, and the state's name behind it at a 0.07 stroke. A Google map of a whole state is a grey field with six identical pins. The geometry is a 660x492 space - 60 units wider than the state needs, so the labels on the right of the eastern hospitals have room on a 320px phone.
- **The drawing is `aria-hidden` and holds no controls a reader depends on**; the rows are the controls. Each dot carries a 17-unit invisible hit circle for a fine pointer (hover previews, click chooses and scrolls the row into view), and nothing on the map is a required tap target on a phone.
- **The three Ahmedabad hospitals are nudged apart in `branches.json`.** At true scale Gota, Odhav and Juhapura sit inside one dot; spread by 30-40 units each keeps its own dot and label. Label sides are per hospital (`map.side`) and were placed so no two names touch on a 320px phone: Visnagar, Gota and Juhapura read to the left, Himmatnagar, Ahmedabad and Bharuch to the right. Re-check every width if a point moves.
- **Lines and dots are SVG; the labels are HTML in percentages over the scene**, at a real type size (BranchMap's rule). The scene keeps the drawing's proportions (`aspect-ratio: 660 / 492`) at every width so the percentages always land on their dots; where the card is wider than the scene, the navy carries on either side. `translate`, never `transform`, on the labels - framer writes their fade-up to `transform`.
- **The lit hospital's label turns into a white pill in place - that is the map's readout.** A card floated over the dot with the name and the street was built and removed twice: at rest it covered the labels of the two other Ahmedabad hospitals, and on hover it only repeated what the pill and the lit row already said. The pill grows out of the label's own margins (`padding: 3px 8px; margin: -3px -8px`) so the text never moves, and it grows outward from the dot, so a pill on one side of the cluster never reaches a label on the other.
- **It plays when it comes into view** (`useInView`, `amount: 0.35`, once): the fill lands, the outline draws itself (1.7s), the route follows through a mask (a `pathLength` animation replaces the dash pattern and the line comes out solid - BranchMap's trap), and the dots land north to south on a spring with their labels a beat behind. Under reduced motion everything is already drawn: 0 animations, every label and pin at opacity 1, verified on phone and laptop.
- **One thing keeps moving afterwards: the traveller**, a dot that rides the route from the hospital that was lit to the one that is. Each hospital's place along the route is measured once from the drawn path (`getPointAtLength`, 720 samples) rather than assumed from the point list, and the position is written straight to the DOM on every frame of the spring - it is a measurement along a path, not render state. It fades in after the route has drawn and does not exist under reduced motion.
- The head-office dot carries a dashed ring; the lit dot grows (`r` is transitioned as a CSS property), takes a glow and, with motion allowed, two ripples.
- The OPD status pill (`BranchStatus`, the hospital page's component) sits bottom left over the sea - the one corner empty at every width - and drops its detail line on phones. It takes the lit hospital (`activeBranch`), so it is part of the map's readout: the six can keep different hours, and the pill answers for whichever row is lit rather than stating one figure for all.

## One hospital: /branches/:slug

**Six blocks, each answering one question a visitor has about a building**: what is this place (the hero), where is it and how do I reach it (the locate band, on the page's one dark ground), who will I see (the team), what can be treated here (care), what does it look like inside (the mosaic), and is another hospital closer (the way on). Everything else that moves here answers the reader (a tab, a photograph opening, a row leaning toward its page) or settles once and stops (the hero photograph's 10s push from 1.05). There is no loop on this page except the map's pin and that dot, and both are pointing at something.

**The phone is not the desktop page stacked, and that is the whole second pass on this page.** The first build laid every block out in one column and ran to 5450px on a 390x844 phone - six and a half screens, most of it label-above-list - and it read as complex and inert: the first screen offered one button, the locate band was a 1504px wall, and nothing on the page answered a tap. The reference was Disha Eye Hospitals' single-hospital pages.

### BranchLocate and BranchMap

`src/sections/BranchLocate.jsx` is the navy band: a drawn map beside the address, the landmarks, the desk numbers and the hours. `src/components/BranchMap.jsx` is the drawing. **This is the page's signature section and the one the reader is meant to enjoy.**

- **The clock is the hospital's, never the device's.** A patient in Visnagar and a son in Toronto must be told the same thing, so the weekday and the time are read through `Intl.DateTimeFormat` in the hospital's time zone (`hospitalNow` in `lib/hours.js`). It re-resolves every 60s, so a page left open crosses 6:00 PM correctly. **The state is resolved in render, not held**: the pill takes a `branch` prop and the branch changes under it on the switchboard, the slip and the index map, so a held value would go on describing the old hospital until the next tick - the tick is a bare counter that only forces the re-render.

- It sits in the body column under the heading at every width. In the label column it read *ahead* of the heading the moment the two stacked on a phone.

A schedule with a Saturday half day or a lunch break is a second slot, and `getOpenState()` answers between slots (`Opens 4:00 PM`), after the last slot (the next open day's first opening) and on a day with no slot (`closedToday`, worded with the hospital's `closedNote`). The Hours tab's hedge is the block's `note`, and a hospital without one prints none.

- **The map is a sketch of the postal address, not an embed.** Every element on it is a fact from the address - M.N. College Road, New Court, GEB, the PIN - laid out the way a local would draw it on the back of a card. A Google map at this size is a grey field with one pin and tells a first-time visitor nothing they can repeat to a driver; the sketch names the things they will look for. `Show live map` swaps the sketch for the Google embed inside the same frame (`LazyMapFrame`, loading on toggle), and `Show sketch` brings it back.

Under `prefers-reduced-motion` every stroke is already drawn, there are no ripples and no traveller; verified 0 animations and every label at opacity 1.
- **The dashed centre line is revealed through a mask, not a `pathLength` animation.** framer's `pathLength` replaces `stroke-dasharray` with its own and the line came out solid; a masked path draws along the road and keeps its dashes.

The pin card is centred above the pin (`translate: -50% -100%`) with a `::after` pointer.

Anchored left and right with a `46%` cap, every label grows inward and wraps rather than clipping, whatever an address happens to name. Re-check clipping on **all six** hospitals after touching this, not just one. **The right-hand label hangs from its top edge (`translate: 0 0`, `top: 47.5%`) rather than centring on its block's row**: a name that wraps then grows downward into open ground instead of upward into the hospital block - `Gujarat Vepari Maha Mandal` on two lines reached the hospital's own block and the traveller on the Ahmedabad map at 320-360px. The left label stays centred; its block is at the foot of the drawing and nothing sits above it.

- The head is the contact page's: centred serif with the promise in italic accent (`Tell us when, / we hold the slot.`). The lede is hidden below 641px, as on the contact page, so the first step reaches the first screen.
- **The five steps and their fields**: `who` (patient name, mobile - both required), `where` (the hospital, required, preselected), `what` (the reason - one of the eleven services or `Not sure yet`, required, preselected from `?service=`), `when` (a day and a time of day, both optional), `send` (an optional note, then Send). Enter in a text field is Continue.
- **The rail across the top is five dots on a track that fills behind the reader.** Five equal grid columns put the dot centres at 10/30/50/70/90%, which is why the track runs 10% to 90%. A step reads as answered (check) when it is complete and not current - at once for a required step, because a hospital or treatment the reader arrived with *is* an answer, and only once passed for an optional one, because "nothing chosen" is not an answer until the question has been seen (`REQUIRED_STEPS`). A visited step can be reopened from the rail; a step ahead cannot be skipped to (`furthest`). The rail carries no answer text under its labels - the slip carries the answers, and a first build's ragged two-line summaries under 60px columns were removed.

Verified: choosing Ahmedabad stores `ahmedabad` and the header's number reads `tel:07922901515` at once.
- **`ChoiceGroup` is one radio group of chips serving four questions** (hospital, reason, day, time): `role="radio"`, `aria-checked`, a roving tabstop, arrow keys walking one flat list even when the options are read in runs under headings (the reasons are grouped by kind of care, the services index's order), the chosen chip's tint as one element that travels (`layoutId`), and a ring that fills accent and draws a check so "this one" is never only a colour. Three shapes by `data-shape`: `row` (two columns from 641px, **full-width rows on a phone** - in a 160px column `Comprehensive Glaucoma Care` ran to three lines under the ring), `tile` (the day rail) and `segment` (`auto-fit, minmax(122px, 1fr)`, so the time of day is four across where it fits and two by two where it does not - a fixed four wrapped `Any time` beside the slip at 1024px).
- **The day is a rail of tiles, not a date input.** `Any day`, then the next ten open days **of the chosen hospital**, on its clock (`getOpenDays(branch)`: its own closed days skipped, and today dropped once its OPD has closed for the day - the rail is rebuilt when the hospital changes), then `Pick a date` which reveals a native date input for anything further out. Dates are ISO strings handled at UTC noon so adding days and reading the weekday can never drift across a midnight in the reader's own zone. The schema refuses a past day or a closed day either way, so a Sunday typed into the date input is caught with the same error - **as an object-level `superRefine`, not a field refine**, because which days are closed depends on `values.branch`, and only the whole form knows that. That is also why `isStepComplete()` runs one full parse and reads the issues for the step's own fields rather than `pick()`ing a sub-schema, which would drop the object-level check from the one step that needs it (zod 4 still runs the refinement when other fields carry continuable errors - verified). The error and the note under the rail are templates filled from the hospital's block (`Choose an open day (Monday to Saturday)...`; `Sunday is not offered here: the Visnagar OPD is emergency and prior appointments only.`), and a hospital open every day gets no note. The chosen tile carries an accent bar along its foot in place of the ring, and the rail fades at its right edge, which is what says it continues.
- **The mobile field carries a `+91` in its margin that steps aside when the reader types a plus.** `parseMobile` reduces any input to its digits, drops an Indian `91` or trunk `0`, and accepts a ten-digit mobile starting 6-9 - or, with a leading plus, any 8-15 digit international number (a son booking from Toronto). The slip and the message carry the formatted form (`+91 98765 43210`).
- **Send is a plain `<a>` to `wa.me`, never `window.open` after an awaited validation** - that is what popup blockers exist to stop. The link is only reachable through the steps, so it is pressed on a complete request; if it somehow is not (`ready` is a synchronous `safeParse`), the click is cancelled and the reader is taken to the first step still missing something. Pressing it sets `sent` and the card becomes the receipt: what to do in WhatsApp, the OPD hours, `Open WhatsApp again`, `Edit request`, and `Book for someone else` (which clears the patient fields and keeps the hospital). The slip's stamp turns from `Ready to send` to a green `Sent`, and its note changes with it.
- **The message** (`buildAppointmentMessage`): a bold heading naming the hospital, one line per field in the JSON's own templates - patient, mobile, reason, preferred day (`Any day` when none), preferred time (`Any time`), note - with an empty line dropped rather than sent as `Note: -`, and a closing line. Verified end to end: `wa.me/919998807891?text=*Appointment request - Aakash Eye Hospital, Ahmedabad* ... Preferred day: Wednesday, 16 September 2026 ... Please confirm a slot. Thank you.`

### The motion, and the rule it follows

**Things arrive in sequence, progress is seen to travel, and the slip shows where the reader is writing.** None of it is decoration, and every piece renders finished under `prefers-reduced-motion` (verified: 0 animations on load and after a Continue).

- **The head's promise writes itself in** - `we hold the slot.` is revealed left to right by a `clipPath` inset once the line has risen. The one flourish the head has.
- **The rail assembles**: the track draws across (`scaleX`, 0.45s in) and the five dots pop in on a spring, 80ms apart. **Moving forward, the dot the fill reaches takes a one-shot ring** (`.is-hit` on the dot, written by `go()` after `RAIL_HIT_MS`, the contact jack's device) - progress is seen to arrive, not to switch.
- **Every step assembles chip by chip.** `ChoiceGroup`'s chips carry the panel's named `enter` / `center` / `exit` states and the group wrapper staggers them at 35ms (`groupVariants` in `BookingSteps`), so a step's answers land behind its head rather than as one block. **Choosing sends one ring out from the mark** (`.ap-chip__mark::before`, a CSS animation that runs when `data-on` starts matching - which is also when a panel opens on a chip already chosen, and that is the reader being shown their current answer).
- **The slip prints itself.** Its lines arrive in sequence when it mounts - on a laptop with the page, on a phone inside the last step, where the reader watches their request print. **A pen sits in the margin beside the line being written** and travels down the slip as the reader goes (`activeLine` from the step, `layoutId="ap-slip-pen"`; on the first step it moves from Patient to Mobile once a name is in). **A chosen answer lands with a highlighter sweep** across its line (`.ap-slip__wash`, keyed on the value so it runs once per change). The teal light in the navy head drifts on an 18s loop, at the same strength the contact card carries, so nothing measured on it changes.
- **A mouse over the desktop slip tilts it** (`rotateX` / `rotateY` on springs, 3.5deg, mouse pointers only, never on the compact slip) - what says it is paper and not a panel.
- **The send button arrives with one sheen** across it and a small wave of the WhatsApp glyph; Continue's arrow leans on hover.
- **The receipt's check mark sends two rings out** (`::before` / `::after`, `ap-ring`) - the pin's ripples on the hospital map, for the same reason: something just landed. The rings stop at 1.65x because the mark sits at the card's padding edge and a wider ring is cut off on a phone.

## Opening curtain

`src/components/AppPreloader.jsx` is the first thing a visitor sees, once per session, and it owns `src/styles/preloader.css` (`.pl`) together with `HydrateFallback.jsx` (`.pl--wait`) and `IntroMark.jsx`, the composition both render - the iris, the wordmark and one serif line. The timing constants, the storage key, the done event, `introElapsed()` and `useIntroDone()` live in `src/lib/intro.js`, which the hero and the cookie sheet read - the three never read each other. `splitTagline()` is in `src/lib/brand.js`, plain JS with no React import, because `vite.config.js` reads it too.

**It is a curtain over a load, not a timer over a finished page.** The build it replaced was a navy splash with an orbit spinner, a scan line, breathing rings, a background grid, a fake progress bar, a gradient stripe and the hospital's name printed three times, on a fixed 1.9s timer that started *after* the home page was in the DOM - measured: `.e-hero` mounted at 142ms and the splash held it hidden until 2089ms, behind a white `HydrateFallback` spinner that showed first. It also left the page live underneath (a swipe scrolled it, Tab reached the header) and let the hero film run unseen. All of it is gone, with its ~260 lines in `global.css`.

- **The first frame is static HTML in `index.html`**: paper, the pupil seed, the wordmark and the line, in a `<style>` and a `<div id="app-intro">` before `#root`, so there is never a white flash, a spinner or a lone dot ahead of the curtain - a slow first load sits on a proper brand frame, not a seed. The wordmark path and the tagline are `%BRAND_*%` tokens filled from `site.json` by the `brandHtml()` plugin in `vite.config.js` (dev and build), so the brand is written once. An inline script stamps `window.__aakashIntroStart` and adds `intro-seen` to `<html>` when `sessionStorage.aakash_intro_seen` is set, which hides the frame before first paint; a 6s CSS animation hides it if JavaScript never runs. `AppPreloader` paints the identical frame on top and removes the static one in its mount effect. **The geometry is duplicated on purpose** - `--pl-iris`, `--pl-lift`, the copy block and the `max-height: 520px` rule in `preloader.css` are repeated in the inline style - and it has to stay identical: measured, the static and React seed centres, wordmark boxes and line boxes coincide to 0.05px at 320x568, 390x844, 844x390, 740x360, 1440x900 and 1920x1080. Change one, change both, and re-measure.
- **The wordmark and the line rise the moment they can be shown properly, and React resumes them mid-flight.** They do not wait on the iris choreography - on the static frame nothing else is moving, so a scheduled 380ms was 450ms of a lone dot on a slow load, the same fault the wait frame had. Instead a script at the foot of the static frame waits for the logo to decode and the serif to load (`document.fonts.load`, both faces; the inline script runs after the render-blocking Google stylesheet, so the faces are known by then), then stamps `--pl-ready-at` on `<html>` and adds `pl-ready`, which starts both rises (0ms and 100ms, 420ms each); a 1500ms timeout starts them regardless. The line therefore never paints in Georgia and swaps. `AppPreloader` stamps `--pl-t` (`introElapsed()`) **in a `useLayoutEffect`, at commit and before paint** - stamped at render it ran up to 160ms early and the wordmark visibly stepped back at the swap - and removes the static frame in the same pre-paint step so the two frames never overlap. The rises in `preloader.css` carry `calc(delay - max(0ms, var(--pl-t) - var(--pl-ready-at)))`, so React lands exactly where the frame left them, and takes the full delay if it arrived before the assets did. Measured across the swap frame: wordmark 0.968 -> 0.981 and 0.756 -> 0.886 on the same curve, with no frame showing both. The iris draw-in starts at mount regardless - seed and identity first, then the iris opens round it.
- **It lifts when the first screen is ready**, not on a clock: `document.fonts.ready` and the decoded first picture under `main` (the hero poster, a hospital's facade), read from the DOM two frames after mount because the hero picks its phone encode in an effect of its own. On `/` it also holds `INTRO_FLOOR_MS` (1100ms) **from the static frame's first paint**, so a slow load spends the floor before React arrives and adds no hold of its own, but never less than `INTRO_DRAW_MS` (1000ms) from mount - the aperture must not open over a half-drawn iris, however late React came. Every other route has no floor. `INTRO_CAP_MS` (3200ms, same clock, same draw-in guard on `/`) lifts it regardless. A curtain that was up for less than `INTRO_QUICK_MS` (420ms) on a non-home route is dropped, not opened - an aperture over nothing reads as a glitch. Measured on a warm load: static frame at 19ms, curtain swap at 139-176ms, lift at mount + 1000ms, gone 850ms later on `/`; on `/services/cataract-surgery` up at 129ms and dropped at 350ms. Every draw-in animation finishes by 1000ms from mount; if one is lengthened, `INTRO_DRAW_MS` moves with it.
- **Nothing under it is live.** `body.pl-lock` and `touch-action: none` stop scrolling (a real touch drag and a wheel both leave `scrollY` at 0), and every other child of `#root` gets the `inert` attribute while the curtain is up (Tab lands on nothing). Attributes and `classList`, never property writes - `react-hooks/immutability`.
- **The mark is an iris that draws itself** - the services page's `IrisMark` vocabulary, redrawn here without framer so the root bundle does not pay for it: the pupil is already on screen (the seed), the limbus draws round it, the stroma grows out of it, the body blooms, the rings arrive last, and the wordmark and one serif line rise under it. Every start value is the seed the static frame painted. The line is `site.brand.tagline` with its trailing `since <year>` lifted into the accent italic by `splitTagline()`, the footer's device; nothing on the screen is written twice - the logo already says the name.
- **The exit is an aperture, not a fade.** `--pl-r` is a registered `@property` transitioned from 0 to the viewport's half-diagonal (`hypot()`); the curtain is `--e-accent` masked by that radius, and its `::before` is paper masked 3px wider, so the accent shows only as the rim of the hole as it opens from the pupil onto the page. The content fades in the first 260ms and the corners fade out in the last 240ms, which is also the fallback where `@property` is unsupported. Measured 55 frames in 900ms at 390x844 @3x, worst gap 17ms.
- **Every curtain mask ends on an explicit `#000 100%` stop, and Safari is why.** At rest the curtain's gradient is `transparent -1px, #000 0px`, and Safari (26.6 measured) paints a radial-gradient whose stops all sit at or below zero as almost entirely transparent - one dot at the centre and nothing else. On a Mac the whole hold was see-through: the header, the hero film and the frozen hero copy showed under a curtain that only materialised once `--pl-r` began to move, so on desktop the intro read as not happening at all. Chrome paints the same gradient solid, which is why headless and headed Chrome at every desktop size passed and the phone (Chrome emulation, then a real phone) always did. The trailing stop gives the gradient an extent in both browsers and changes nothing visible in either - verified at rest (no pinprick through the pupil), mid-aperture and after, in Safari and Chrome, at 1440x900 and 390x844. Isolated with a twelve-variant test page: literal `0px, 1px` and `var, var` (both zero) render, `-1px, 0px` does not, so a negative stop with nothing after it is the trigger. **Safari cannot be driven over CDP here** - `open -a Safari <url>` and a timed `screencapture -x -C` loop is how it was seen; `open` gives a new tab, so the session key does not suppress the curtain.
- It fires `INTRO_DONE_EVENT` as it starts to open and writes the session key then, so a reload mid-exit skips it. The hero starts its film and lifts its copy on that event; the cookie sheet waits for it.
- Dismissible after `INTRO_DISMISS_AFTER_MS` (500ms) by a tap, Enter or Escape. It is `role="status"` with an `aria-label`; the iris is `aria-hidden`.
- **Reduced motion: no floor, no draw-in, no aperture.** Decided in JS (`matchMedia`, read once into `still`) and written as `data-still` on the root; `preloader.css`'s `[data-still]` block sets every part's finished state with `animation: none` - the global rule zeroes durations but not delays, so a 480ms delay would otherwise be 480ms of nothing. The curtain is up only while the first screen is genuinely loading and then unmounts. Measured: 0 running animations, up 180-202ms.
- **A phone held sideways gets a smaller mark** (`max-height: 520px`): at 844x390 the copy ran 54px past the bottom. The mark gives, never the type; measured copy bottom 327px in 390 and 314px in 360.
- **`HydrateFallback` is bare paper, and then the finished mark.** It fills the gap between React's first render and the first route module on an in-session reload. A cached route arrives in 50-150ms, so for `SETTLE_MS` (350ms) it is paper and nothing else - nothing flashes, and there is no lone dot (the first build pulsed the seed there, and a black dot alone on white for the length of a chunk fetch is exactly what a loader must not look like). Only a genuinely slow reload gets the mark: `IntroMark` still (`data-still`), faded in over 320ms, in the curtain's exact geometry. **On a first visit it renders `null`** - the static frame is the frame, and painting a finished iris over its seed and then restarting the draw from the seed was a visible jump on a throttled load. Measured: fast reload 52-145ms with the stage never rendered; throttled reload mark visible from 350ms after mount until the route arrived.
- The logo is `public/assets/logo.png`, the one file the header, the drawer, the footer, this curtain, `index.html`'s icons and the JSON-LD all read through `site.brand.logo`. **It is a 720x240 encode of the hospital's 3552x1184 master** (`~/Downloads/logof.png`), which replaced a 210x70 file that was being stretched 1.6-1.9x on every Retina and phone screen and read as blurry in every header. 720px covers the largest render (178px on a tablet) at 4x. **The master's "transparent" background is opaque white** (alpha 255 everywhere, pixels at 252-254 rather than 255), so it is keyed, never used as shipped: white-matte removal (`alpha = 255 - min(r,g,b)`, colour un-premultiplied against white) over the whole image, with the blue emblem square (bbox 0,0-870,853 in the master) forced fully opaque because its white is paint, not background; then alpha under 16 zeroed and over 240 snapped to 255, because the source's near-white noise left a haze that PNG could not compress (178KB) - cleaned and quantised to 128 colours it is 29KB with no visible fringe on navy at 3x zoom. Re-encode from the master with that recipe, never edit the shipped PNG. Verified on the header (390 and 1440px), the footer's warm paper and this curtain: sharp, and no white box on the paper grounds. An SVG wordmark is still the better master if the hospital has one; nothing else changes when it lands.

## Header

`src/components/Header.jsx` follows the Narayana Health reference layout and is the only consumer of `src/styles/header.css`.

- Desktop (>= 1041px): a brand row (logo, `Since 1993` lockup, emergency helpline, selected-branch phone, branch picker, Book Appointment) above a nav row carrying the primary links. The lockup is decorative and hides below 1200px so the contact details and CTA are never squeezed out. The header at rest is 133px here and 109px below 1041px (`--hd-height`).
- Everything in the header aligns to the container edges: the logo, the first nav link text, the rule between the two rows, and the trailing CTA. Nav spacing comes from `gap`, not from link padding, so the first link and its active underline stay flush with the logo. Verify alignment by measuring, not by eye.
- Mobile (<= 1040px): **one 65px row** - logo, the emergency link and the menu button - and the nav row is replaced by a right-side drawer. **There is no branch bar on a phone.** Two builds had one above the brand row, navy and then white, and both were wrong for the same reason: a 44px band across the top of every phone screen spent on one control, sitting directly under a browser toolbar whose colour the page does not control (`theme-color` where honoured; near-black on Chrome for Android in dark mode, which ignores `theme-color` entirely - tested, and an open Chromium issue). Every big multi-branch hospital keeps a location control; none gives it its own band on a phone. **The phone's selector is the drawer's branch block**, which sits directly above the Call OPD / WhatsApp / Directions actions it changes - see the drawer section. Desktop keeps its picker in the brand row, where there is room.
- **Do not add a first-visit "choose your hospital" prompt.** A first visit already has the opening curtain (about 2s on the home page) and the consent sheet that follows it; a third interruption before the page is what makes people close the tab. Most first-time visitors do not yet know which branch they want, so the answer would be a guess, and a guessed branch is worse than the head-office default. It would also fight the consent sheet for the same z-index and thumb zone. The drawer's first-open expansion (below) is the non-blocking version of the same idea.
- `index.html` sets `theme-color` to white so the toolbar merges with the white header on iOS Safari and light-mode Chrome, and declares `color-scheme: light`. Do not set it back to navy: nothing at the top of the page is navy any more.
- **`--hd-navy` and `--hd-blue` read `--e-navy` / `--e-navy-2`, the design system's own pair.** They used to read the legacy `--color-brand-blue*` tokens, and `global.css` carried a stray second `:root` (a leftover "professional theme" block) that re-declared those to a brighter `#1556a6` / `#d91c7a` with a 16px radius; the header only rendered in the site's navy because `ThemeTokens.jsx` overwrote the tokens inline at mount. That block is deleted and the header reads the same tokens as the footer and every page, so the three can no longer drift. The remaining `--color-*` reads in `header.css` (slate, clinical tint, radii) resolve from the one `:root` at the top of `global.css`, which matches `theme.json`.
- **The header's buttons - `.hd__cta`, the branch picker, `.hd__ghost` and the drawer's `Change` toggle - are set in `--e-sans`, the face `.e-btn`, the cookie sheet and the footer's buttons use.** Names, the nav row and the drawer rows stay in `--font-heading` (Inter Tight), the way the footer sets its column heads in `--e-tight` and its links in `--e-sans`: wayfinding is set in the heading face, controls in the UI face.
- **The `Since 1993` lockup is the footer's masthead lockup, set once.** `splitEstablished()` lives in `src/lib/brand.js` beside `splitTagline()` and both `Header` and `Footer` read it: the tracked micro word, the year in the serif italic accent, and (in the header only) the `Trusted eye care` note beneath. As `Since 1993` in bold navy Inter Tight it was the one fact the two ends of the page set two different ways, and it left the header as the only surface on the site with no trace of the serif accent every page opens on. The row is unchanged at 76px; the lockup still hides below 1200px.
- **The row heights live on `:root`, not on `.hd`**, so `--hd-height` can be derived from them and read outside the header - it is the header at rest (brand row + border on phones and tablets, 65px; brand row + nav row + border on desktop, 133px), and the landing hero sizes itself to the first screen with it. On phones the compact state is the same height, so scrolling never changes the header's height there; on desktop it shrinks the brand row by 12px.
- The header keeps a selected branch in `localStorage` (`aakash_selected_branch`). It drives the displayed OPD number, the Book Appointment query string and the drawer call/WhatsApp/directions actions, and it adopts the branch whenever a page is opened for a specific one - `?branch=<slug>` on the index, or the `/branches/<slug>` path of a hospital's own page - so the number at the top of a hospital page is always that hospital's.
- Nav items come from `navigation.header`. An item carrying a `dropdown` key renders a menu instead of a link - `"branches"` for the hospitals menu and `"about"` for the two About pages - and its label comes from that JSON entry rather than being written into the component. Header labels and the emergency number live in `site.header`.
- **The phone's logo width has its own scrolled rule.** `.hd--scrolled .hd__brand img` in the `1040px` block outranks the bare `.hd__brand img { width: 132px }` in the `560px` block on specificity, so on every phone the logo grew from 132px to 140px the moment the reader scrolled past the compact threshold and shrank back at the top - measured at 320, 360 and 390px before the `560px` block gained `.hd--scrolled .hd__brand img` alongside it. The compact state on a phone changes nothing visible; keep it that way.
- **A dropdown's `onClose` only clears `openMenu` if that menu is still the open one** (`setOpenMenu((current) => (current === item.dropdown ? null : current))`). Each `NavDropdown` closes on a 160ms timer after the pointer leaves, and a pointer that reaches the other trigger inside that window opened it first - so an unconditional `setOpenMenu(null)` from the stale timer shut About a beat after it opened. Verified with real pointer travel in both directions and from inside the hospitals panel.
- **`header.css` ends with five sibling media blocks - `1040px`, `1199px`, `560px`, `370px` and `prefers-reduced-motion` - and each must close before the next opens.** The `1040px` block lost its closing brace when the city-bar rules were cut out of it, and the four blocks after it silently nested inside: the `Since 1993` lockup stopped hiding between 1041 and 1199px, and the header's reduced-motion rule only applied on phones. The file still parsed, so nothing failed loudly. Count braces (`{` minus `}` must be 0) after deleting a rule near the end of the file.
- **A fine pointer's click on a menu trigger keeps the menu open; it never toggles.** Hover has already opened it, so a plain toggle made a click on `About` close what the hover just showed, and the menu would not come back until the pointer left and returned. `NavDropdown` reads `canHover` and passes `true` on click there; touch and keyboard, which have no hover, still toggle.
- **The dropdown panel never scrolls - its list does.** `overflow-y: auto` on `.hd__mega` clipped the panel's own caret and the transparent `::before` strip that bridges the 10px gap to the trigger, so the caret was never seen and a pointer resting in the gap closed the menu. `.hd__mega-list` carries the viewport cap (less 125px for the panel's head, foot and padding) and the scrolling; measured on a 1280x600 window the six cities scroll under a pinned `View all hospitals`. Do not put overflow back on the panel.
- Both menus are the same component, `NavDropdown`, which owns the `.hd__mega*` rules: one narrow column, hover-open gated on a fine pointer, a close timer over the gap, and roving `ArrowDown`/`ArrowUp`/`Home`/`End` focus with `Escape` returning focus to its trigger. It takes rows and an optional footer link, so the hospitals menu keeps `View all hospitals` and the About menu has no footer. Triggers are held in one `dropdownTriggers` map keyed by the dropdown name, which is what lets `Escape` focus the right one. Do not fork it for a third menu - add rows.

### Hospitals menu

The hospitals menu is `NavDropdown` fed by `branches.json`; the drawer renders the same list as `.hd__drawer-branch-link` rows.

- It is a **single 340px column**, not the 660px two-column mega panel it replaced. Six short city names read faster in one column, and a narrow panel sits under its own trigger instead of spanning half the header - the wide version was a white slab dropped over the hero with no visible relationship to the link that opened it.
- The panel is offset left by `--hd-mega-inset` (22px, its own padding plus the row padding) so the branch names line up under the nav label, and a small caret points back at the trigger.
- The six identical `MapPin` tiles are gone. They repeated the same glyph six times and told the reader nothing; the row now carries name, `Head Office` tag and locality, with a check on the branch the reader is on (or has selected) and a chevron that appears on hover only. Six permanent arrows would be the same mistake as six pins.
- The check marks `activeSlug ?? selectedSlug`, and `aria-current="page"` is set only when the URL is actually showing that branch. It is deliberately **not** the magenta inset bar the drawer's nav links use - that bar means "the page you are on", and "your hospital" is a different claim.
- A 10px gap sits between the trigger and the panel, so the panel bridges it with a transparent `::before` strip and closes on a 160ms timer. Without both, the menu died halfway through the diagonal travel from the link to the first row.
- Keyboard: `ArrowDown` on the trigger opens the menu and focuses the first city, `ArrowDown` / `ArrowUp` / `Home` / `End` move between rows, `Escape` closes and returns focus to the trigger. Hover-open is still gated on `(hover: hover) and (pointer: fine)`.
- The panel caps its height against the viewport and scrolls, so a short laptop window still reaches Juhapura and `View all hospitals`.
- Below 1041px there is no dropdown at all - the drawer's branch block carries the same rows at 52px tall with the same check, and on a phone it is the only selector. The route to a hospital's own page is the drawer's summary row (see the drawer section), and each row of `/branches`.
- On scroll past 96px the header compacts (the desktop brand row shrinks from 76px to 64px) and takes a shadow; it expands again below 16px. Those two thresholds are deliberately far apart. Compacting takes height out of the flow above every section, so the browser compensates with scroll anchoring. With a single 24px threshold that jump landed back under the threshold, the header re-expanded, the offset jumped again, and it flickered in place at one scroll position - first seen when phones still had a 44px city bar to collapse, and the guard stays because desktop still gives up 12px. Keep the gap wider than the anchoring jump if a row height or the threshold changes, and re-measure by resting at y=30-50 and counting class changes per frame.
- The header slides away at every width (`hd--hidden`, a `translateY(-100%)` transform) while the reader scrolls down, and returns on the first scroll up. It reclaims 65px on a phone and 121px on desktop. There is no bottom bar to fall back on, so the reveal has to be instant at every width - never gate it behind a delay, and never lengthen the scroll-up distance needed to bring it back.
- **Direction is read from travel, never from one frame's delta.** Movement is summed while it keeps its sign and reset the moment it reverses, and the header changes state once the sum passes `TRAVEL` (12px). The per-frame `DELTA` of 6px it replaced failed on real devices: a slow reading scroll of 3-4px a frame never crossed it in either direction (the header neither hid nor came back), and a 120Hz phone halves every frame's delta, so ordinary flicks read as jitter there too. The reset on reversal is what still filters trackpad jitter and an iOS rubber-band bounce.
- **For 350ms after a collapse or expand (`SETTLE_MS`), a frame that moved no more than `SETTLE_NOISE` (16px) is ignored** - that is the size of the scroll-anchoring adjustment the height change causes, and a real flick moves far more than that in a frame, so a flick that crosses the threshold still applies at once. The window used to defer *everything* to a `resolveSettle()` timer, and that design had a hole a real phone found every time: a scroll event under `HIDE_AFTER` set `settledByScroll` and disarmed the timer, so a flick from the top of the page - through 96 and past 160 - that stopped inside the window never applied its direction. The header simply did not hide until the reader flicked a second time, and it read as "the navbar does not go up". Nothing is deferred now and there is no timer. Verified with real touch flicks (`Input.dispatchTouchEvent`) and wheel events: one flick from y=0 hides at y=245 on every phone and tablet size, one wheel burst hides at y=248 on every desktop size, a 3px-a-step drag hides on the way down and returns on the way up, and the drawer-open, under-160px and at-bottom guards are unchanged. **Re-check the flicker before trusting any change here** - resting at y=30, 40, 50 and 96 gives 0 class changes in 1.6s, and y=100 gives exactly 1 (the collapse itself; on desktop the offset then reads 88, which is the anchoring adjustment doing its job).
- The hide is guarded so it can never trap the user: it does not engage above 160px of scroll, while any dropdown or the drawer is open (`menusOpenRef`), at the very bottom of the page, or while something inside the header carries a **visible** focus (`.hd:has(:focus-visible)`). A route change resets it. **That guard was `.hd:focus-within`, and it was the second half of "the header does not hide on my phone but does after a reload"**: closing the drawer returns focus to the menu button (correct for keyboard readers), a scroll gesture is not a tap so nothing on a phone ever blurred it again, and the header sat pinned at `transform: none` with `hd--hidden` on it through every scroll until a reload dropped the focus. Programmatic focus after a tap does not match `:focus-visible`; Escape from a keyboard does, so a keyboard reader who closes the drawer still keeps the header. Verified: after a touch open-and-close the header hides on the next flick with focus still on the button; after an Escape close it stays until the button blurs.
- The header is `position: sticky` and hides with a transform, so nothing reflows and the page never shifts when it moves. Keep it that way - animating height or toggling `display` here would cost layout on every scroll frame.
- `html` carries `scroll-padding-top` in `global.css` so anchor targets land below the sticky header rather than under it.

The drawer is the `.hd__drawer*` rules in `header.css`, and it is a navigation menu first: the reader opened it to go somewhere.

- **Order is nav, then actions.** The panel is a fixed head, a scrolling middle, and a footer pinned in the thumb zone (Book Appointment, then Call OPD / WhatsApp / Directions as a three-up). Before this the CTA, two ghost buttons and a four-line address block sat *above* the links, so a 390x844 phone showed three of the routes and the reader had to scroll a menu to reach Gallery or Contact.

Measured: the close button's rect equals the menu button's at 390, 560, 561, 768, 1024 and 1040px. Two tiers are 145px. The emergency line is never more than one glance away: it is at the top of the header when the drawer is closed and at the top of the sheet when it is open.

Verified with a real touch on the backdrop, with Escape, and by tapping inside the sheet.

The block at the top of the scroll area is now the only place a hospital is named: a summary row (`Your hospital`, name, locality) that expands to the six cities under a `Choose your hospital` heading - the heading is what keeps the checked row from reading as the summary printed twice. The nav row of the same name is an ordinary link to `/branches`, like every other row.

They used to link to `/branches?branch=<slug>`, which was fine as a second route while the city bar did the selecting; as the only selector, a control that navigates away is a detour. `View all hospitals` remains the way to that page.

The summary is the one place the drawer names a hospital, so it is also the way to it: `Your hospital / Visnagar ›` opens `buildBranchHref(selectedBranch)` and closes the drawer, and choosing another city retargets it in place (verified: after choosing Bharuch the link reads `/branches/bharuch`). Verified: a fresh visit opens with `aria-expanded="true"` and six rows; after choosing, and on the next visit, it opens collapsed. ## Footer

`src/components/Footer.jsx` follows the Function Health footer and is the only consumer of `src/styles/footer.css`. It renders on every route through `RootLayout`.

- The shape is the reference's: **one rounded card inset on a warmer ground**, with the fine print left outside the card on the ground itself. The card is `--ft-card` `#f8f7f3` and the ground `--ft-ground` `#e6e3db`; both are local to `.ft` rather than global tokens, because nothing else on the site uses this pair.
- It is **light, not the navy it used to be**. Three reasons, in order: `PatientStories` ends the home page on `--e-navy`, and two adjacent dark bands in slightly different navies read as a mistake rather than as a footer; the logo is a magenta-on-transparent wordmark that needed a white pill to survive on navy, which looked like a patch stuck to the page; and this is the densest block of small text on the site, where dark-on-light is the easier read for the older patients the site is built for.
- The inset above the card is `padding-top` on `.ft`, never `margin-top` on `.ft__card`. As a margin it collapsed straight out of the footer's box and the page background showed through as a white strip between the navy section above and the footer ground - visible on every page.
- **Every control in the footer is the header's 4px rectangle (`--ft-radius`), not the reference's pill.** The site's button is the small-radius rectangle - `.e-btn` is 3px, the cookie sheet 3px, the header 4px - and the footer's pills (primary, ghost, the two utility buttons and the social circles) were the one surface disagreeing with the button directly above them on every page: `Book Appointment` at the top of the page and `Book an appointment` at the bottom were two different shapes. The social marks are 42px squares on the shape of the header's menu button rather than circles for the same reason. The card keeps its 18-26px radius - it is a container, not a control. The landing hero's phone pill is the deliberate exception and is documented under Hero.
- The reference's app QR and store badges are dropped: there is no app. Its newsletter block is dropped too - there is no list to subscribe anyone to, and a form that posts nowhere is worse than no form. The action block that replaces it keeps that slot's position and typography (serif headline, italic accent from `--e-accent`, one line of support, then the buttons).
- The masthead is the wordmark plus a `Since 1993` tag, nothing else. A 25-word summary paragraph used to sit beside the logo and was removed; the tag keeps that row from reading as an empty band, and everything the paragraph said is on the page above it.
- The `Since 1993` tag is set in two parts, not one label: `SINCE` stays the tracked 0.72rem micro word the footer uses for contact labels, and the year is the serif italic accent (`--e-serif`, `--e-accent`), baseline-aligned beside it behind the hairline divider. As one uppercase micro string it read as a caption stuck to the logo; the serif year makes the pair a lockup and repeats the serif/italic pairing of the action headline and the hero accent. `splitEstablished()` reads the year off the end of `site.header.establishedLabel`, so the JSON stays one plain string and a label with no trailing year still renders whole. Measured with no overflow and one line at 320, 390 and 1440px.

**Bands, in DOM order, which is also the reading order at every width.** No `order` tricks - the visual order and the tab order are the same everywhere.

1. `.ft__masthead` - logo and the one-sentence summary.
2. `.ft__reach` - the OPD/emergency phone, the email and the OPD hours of the reader's hospital (the one the header stored, followed through `BRANCH_CHANGE_EVENT` and named in the label: `OPD hours · Visnagar`), with the emergency note under them behind an accent rule. The strip is `auto-fit` with a `260px` minimum rather than a fixed three columns, because the email is 26 characters at 1.12rem: at 768px a hard three-column grid ran it straight into the `OPD HOURS` label in the next cell. It drops to two columns at about 830px of card width and to one on a phone, with no breakpoint to keep in sync with the type size. These were first written into the action column and made it 420px taller than the link columns beside it, which left the bottom-left third of the card empty; as their own full-width band they fill the width, and on a phone the phone number lands second in the footer instead of below eighteen links.
3. `.ft__body` - three link columns plus the action block, which is explicitly placed in column 4 on desktop and falls to a full-width two-column band at <= 1080px.
4. `.ft__utility` - social pills on the left, `Privacy and cookie preferences` and `Back to top` on the right.
5. `.ft__fine` - the medical fine print and the copyright, outside the card.

**Content sources.** Nothing in the footer is hard-coded.

- `site.footer` holds `summary`, `hospitalsTitle`, the `cta` block, `contactLabels`, `emergencyNote`, `disclaimers`, `legalNote` and `copyright`.
- `navigation.footer` holds exactly the two link columns that are pages - `Treatments` and `Hospital`. The third column is the six branches, derived from `branches.json` and titled from `site.footer.hospitalsTitle`, so the branch list can never drift from the rest of the site. Every branch link is `/branches?branch=<slug>`, which the header adopts as the selected branch, so a footer branch link also sets the OPD number shown at the top of the next page.
- The phone is `site.header.emergency.phone`, which is currently the same number as the Visnagar OPD line - hence the single row labelled `OPD and emergency helpline` rather than two rows carrying one number twice. If the hospital ever separates them, this becomes two rows.
- The social links come from `site.socialLinks` - Facebook, Instagram and X - and render as brand-mark circles, as the reference has them. lucide-react 1.x removed its brand icons, so the three marks are inlined in `socialMarks` in `Footer.jsx` and keyed by the `icon` field in the JSON; a link whose `icon` matches no mark renders nothing, so add the path when adding an account. The circles are icon-only, so each carries `aria-label="<brand> on <platform>"` and its `svg` is `aria-hidden` - three labelled pills took the whole utility row.

**Typography.** The column headings are sentence case at 0.98rem in `--e-tight`, not the 0.72rem tracked uppercase micro-label the rest of the site uses for section labels. Uppercase made them the smallest type in the footer, sitting directly above the links they title, so each column read as one undifferentiated block; at 0.98rem a reader can land on a heading. The micro uppercase style stays on the contact labels, where it labels a value rather than titling a list. Link rows are 0.98rem, contact values 1.12rem, and the fine print 0.84rem capped at `108ch` - it ran the full 1240px shell before, at about 150 characters a line.

- **Two things in the footer never break inside themselves**, both through `.ft__nobr`: the hours value (`9:00 AM - 6:00 PM`), which stranded `PM` alone on a line at 320-390 and 768px and split the range at 1024px, so the line now breaks after `Monday to Saturday,`; and any hyphenated word in the action headline, which `keepCompounds()` wraps so `check-up` never sets as `check-` / `up`. The headline also carries `text-wrap: balance`. Measured line by line with a per-character `Range` walk at 320-1920px. Each open day set is its own `.ft__hours` line (`display: block`), so a Saturday half day reads as two lines. **The label rule is `.ft__contact div > span`, not `.ft__contact span`** - the bare descendant selector caught the `.ft__nobr` span inside the value too and set the time range as a 0.71rem uppercase micro label on its own line, which is what the footer shipped with.
- `.ft__fine p` carries that `108ch` cap, and `.ft__copy` is a `p` inside `.ft__fine`, so the copyright rule needs `.ft__fine .ft__copy` to beat it. Written as a bare `.ft__copy` the cap won on specificity and the rule above the copyright stopped two thirds of the way across the page.
- Footer link labels are written to fit the two-column phone layout: `Bladeless laser`, `Eye check-up`, `Book appointment`. Measured with `Range.getClientRects()`, no footer link wraps at 320, 360, 390, 414, 480, 600 or 768px. If a label is lengthened, re-measure - a wrapped label knocks the two columns out of alignment row for row, which is what the shortening fixed.

**Breakpoints.** 1080px moves the action block out of column 4 into a full-width two-up band; 900px hides the `Head office` label; 860px stacks that band, because below it the copy column is under ~250px and the headline broke to four lines beside a half-empty button column; 720px drops the links to two columns; 380px drops them to one, where two columns are about 120px wide and half the labels wrapped.

**Contrast and targets are measured, not assumed.** On the card: body copy and link text `--e-ink-2` 7.3:1, headings and contact values `--e-ink` 17:1, the italic accent 6.0:1, the fine print 5.5:1 on the ground. Two things were fixed after measuring: the `Head office` label was `--e-ink-3` at 2.97:1 and moved to `--e-ink-2`, and control outlines needed their own token - `--ft-line` is the decorative hairline at 1.3:1 and is fine between bands, but WCAG 1.4.11 wants 3:1 on the boundary of a control, so pills and the ghost button use `--ft-edge` `#948f83` at 3.01:1. **Do not put `--ft-line` on a button, and do not lighten `--ft-edge` to match the rules.** The phone and email links carry `min-height: 26px` so both clear the WCAG 2.2 minimum on their own; measured minimum target across the whole footer is 26px, and there is no page overflow, from 320px to 1920px.

- `Head office` is hidden at <= 900px, where either two branches share a row or the column is about 210px, and the label wrapped the Visnagar row two lines taller than the other five. The branches page carries the same fact.
- `Back to top` honours `prefers-reduced-motion`: an instant jump rather than a smooth scroll across a 6000px page.

## Cookie consent

`src/components/CookieConsent.jsx` renders on every route through `RootLayout` and is the only consumer of `src/styles/cookie.css`. It is two surfaces and one state machine: a **banner** on a first visit, and a **dialog** opened from the banner's `Choose cookies` or from the footer's `Privacy and cookie preferences` link, which dispatches `aakash:open-cookie-preferences`.

- **Every optional category starts off.** `noOptional` is both the initial state of the dialog and exactly what `Reject optional` stores, and it is written out key by key rather than as a bare `{ necessary: true }` - `normalize()` fills missing keys from that same object, so a short payload would have quietly re-enabled a category the reader had just refused. A pre-ticked switch is consent nobody gave; do not default one to on.
- The choice is stored in the `aakash_cookie_preferences` cookie for 180 days and read once through a lazy `useState` initialiser, not in an effect - `react-hooks/set-state-in-effect` rejects the effect version.
- On a first visit the banner waits for the opening curtain's `INTRO_DONE_EVENT` and then `INTRO_EXIT_MS + 500ms`, so it is never slid in behind the curtain; a visit with no curtain (the intro already seen this session) gets it after `BANNER_DELAY_MS` (600ms). It used to be a fixed 2100ms for everyone, coupled to the old preloader's timer by a magic number.
- Its `z-index` is **190, deliberately under the header (200) and the mobile drawer (210)**. The drawer is a full-height sheet with Book Appointment and the call actions pinned in its thumb zone, and a consent card floating on top of those would cover them. The dialog is the surface that takes the screen, at 260.
- The dialog is the only one of the two that locks the page, traps `Tab`, answers `Escape` and returns focus to whatever opened it. The banner stays a layer the reader can scroll past.
- **Closing the dialog without choosing falls back to the banner** whenever nothing is stored yet, so a reader who opens the details and changes their mind is still asked rather than left with no choice recorded.
- Category switches are `role="switch"` buttons rather than checkboxes, labelled by the category title through `aria-labelledby`. The control is 54x32 and a `::after` inset of -6px stretches the pressable area to 44px without growing it. The `Necessary` row carries an `Always on` pill instead of a switch.
- Each category has a `What this stores` disclosure naming the actual cookies. `.ck__cat-list[hidden]` needs its own `display: none` - the `display: grid` on the list would otherwise beat the browser's `[hidden]` rule and the details would render permanently open.
- Phones and tablets get bottom sheets, desktop gets a centred card, and both animate under `ck-rise` / `ck-pop` with every animation and transition dropped under `prefers-reduced-motion`.
- Measured across 320-1920px: no page overflow, no target under 44px, and no button label wraps to a second line. Heights: banner 264px on a 390x844 phone (31% of the screen) and 304px on desktop; the dialog fits with no internal scroll at 1440x900 and 820x1180.
- The phone gets a shorter sentence from `cookies.banner.bodyShort`, swapped with CSS at 720px, the same way the hospital page carries `ledeShort`. Height comes out of authored copy, never out of truncation - the stacked build with the full sentence stood 397px tall, 47% of a phone screen for a notice.
- Contrast is measured, not assumed. On the card: title 18.2:1, lede and note 7.8:1, category summary and detail lines 7.1:1, the magenta eyebrow 6.4:1, the primary button 14.3:1. Control boundaries need `--ck-edge` (`#7f8b96`, the header's edge value): 3.48:1 on the card and 3.16:1 on the footer band the ghost buttons sit on. `--ck-rule` is the 1.2:1 hairline and belongs between bands only - **do not put it on a button, and do not lighten `--ck-edge`**; `#949aa1` measured 2.58:1 on that band.
- All copy lives in `site.cookies` (`banner`, `dialog`, `categories`). The category `items` name real cookies - `aakash_cookie_preferences`, `aakash_selected_branch`, `aakash_intro_seen` - so a new stored value means a new line there.

**Launch note:** the site does not act on the stored preferences yet. `aakash_selected_branch` and `aakash_intro_seen` are written by `Header` and `AppPreloader` regardless of the `experience` choice, and there is no analytics script to gate. Both need wiring to this cookie before the consent notice is truthful.

## UI/UX Standards

- Mobile first: design and test from small screens upward.
- Keep navigation short, obvious, and thumb-friendly.
- Primary actions should be visible and direct: Book Appointment, Call, WhatsApp, Directions.
- Use large tap targets, readable type, strong contrast, and enough spacing for older patients.
- Keep sections purposeful. If a section does not help a patient decide, contact, book, or understand care, simplify or remove it.
- Avoid visual clutter, nested cards, decorative overload, and heavy animations.
- Use real hospital, doctor, branch, and treatment imagery where possible. Avoid generic stock-like visuals when real assets exist.
- Make branch selection easy on mobile; users should quickly choose Visnagar, Ahmedabad, or Bharuch.
- Use icons from Lucide React for actions and navigation cues.
- Preserve accessibility: semantic landmarks, labels, focus states, keyboard access, reduced-motion support, and alt text.
- Ensure every UI works at small mobile widths, tablet widths, laptop widths, and large desktop widths.

## Visual Direction

- The site should feel premium, clinical, clean, and trustworthy.
- Prefer calm medical colors from the existing theme over random new palettes.
- Keep typography readable and polished. Avoid text that is too small, too dense, or squeezed into cards.
- Use motion sparingly for reveal and orientation, not as decoration.
- Keep mobile pages direct and vertically efficient.
- Avoid unnecessary hero complexity. The homepage should get users to care options and contact routes quickly.

## SEO, Trust, And Medical Site Requirements

## Coding Style

- Keep changes minimal, focused, and consistent with existing patterns.
- Do not introduce new abstractions unless they remove real duplication or complexity.
- Prefer clear component names and readable JSX.
- Avoid one-letter variables.
- Avoid comments unless the code would otherwise be hard to understand.
- Use ASCII text unless the file already requires non-ASCII.
- Do not commit changes unless explicitly requested.
